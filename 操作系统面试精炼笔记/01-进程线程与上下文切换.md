# 进程、线程与上下文切换

> 当前面试主入口：[[操作系统面试精炼笔记/00-操作系统知识地图]]
> 本文只讲 OS 执行模型，不重复 Java 锁、CAS 和线程池参数。

## 一句话结论

进程提供独立资源视图，线程是进程内的执行流；线程更轻量但共享进程资源，因此切换成本更低也更容易产生共享状态问题。

## 1. 进程与线程

| 维度 | 进程 | 线程 |
|---|---|---|
| 主要职责 | 资源隔离、地址空间和句柄归属 | 承载指令执行和调度 |
| 地址空间 | 通常拥有独立的虚拟地址空间 | 同进程线程共享代码、堆、文件描述符等 |
| 私有状态 | 进程控制信息、资源表等 | 栈、寄存器上下文、程序计数器等 |
| 创建/切换 | 隔离更强，代价通常更高 | 共享更多，切换通常更轻量 |
| 故障影响 | 一个进程崩溃通常不直接破坏其他进程 | 一个线程的错误可能终止或破坏整个进程 |

“线程是 CPU 调度最小单位、进程是资源分配边界”是面试常用表达，但具体实现和内核对象名称随操作系统变化。

## 2. 内核线程、用户级线程与 Java

- 内核可见的线程由操作系统调度，可真正并行使用多核 CPU。
- 用户级线程由运行库或虚拟机管理，切换可以不直接进入内核，但阻塞系统调用和多核利用要看运行时如何映射。
- Java 传统平台线程通常采用 1:1 映射，由 JVM 封装、操作系统最终调度；不要说 Java 线程“脱离操作系统”。
- Java21 虚拟线程是 JVM 调度的轻量任务视图，多个虚拟线程可挂载到平台线程；支持的等待点可以卸载，但不代表所有阻塞调用都能卸载。

## 3. 上下文切换因果链

```text
线程被时间片耗尽、阻塞、唤醒或抢占
→ 保存寄存器、程序计数器、栈等执行上下文
→ 调度器选择另一个可运行线程
→ 恢复目标线程上下文
→ 继续执行
```

上下文切换不是“只切换一个变量”，会带来调度、缓存局部性和内存管理压力。不要背固定的微秒/纳秒数字，应结合 CPU、内核、JVM 和负载测试。

## 4. Java / Linux 关联

- Java `Thread.start()` 创建的是可调度执行单元；`run()` 只是普通方法调用，不能把二者混为一谈。
- Java 线程的 `Runnable`、`WAITING`、`TIMED_WAITING` 是 Java API 视角；OS 还会有就绪、运行、阻塞等调度状态，二者不是逐项同名映射。
- Linux 可用 `ps -eLf` 观察进程及其线程，`top -H -p <PID>` 查看某进程的线程视图；`ps`、`top` 和服务日志是运维入口。
- JVM 线程栈和程序计数器属于线程私有运行时状态，堆属于进程/JVM 内共享区域，详见 [[java八股文/Java后端面试精炼笔记/03-JVM内存-GC与排查]]。

## 容易答错点

- “进程是调度最小单位”：常见现代系统主要调度线程，但不要把所有系统的实现绝对化。
- “线程没有资源”：线程共享进程资源，但仍有自己的栈、寄存器上下文和线程标识。
- “上下文切换就是 CPU 切换”：还包括保存/恢复状态以及缓存和调度影响。
- “虚拟线程等于协程”：虚拟线程由 JVM 调度，语义和调度机制不能直接等同于所有协程实现。

## 高频追问

1. 为什么线程切换通常比进程切换轻量？——共享地址空间和资源映射更多，隔离工作更少，但仍有上下文和调度成本。
2. 多线程为什么能利用多核？——可调度线程映射到多个 CPU 执行；是否并行取决于 CPU、调度和同步约束。
3. Java21 虚拟线程是否取消了操作系统线程？——没有，载体仍是平台线程，JVM 负责虚拟线程与载体之间的调度。
