# 同步、互斥、Condition、CAS 与死锁

> 当前面试主入口：[[操作系统面试精炼笔记/00-操作系统知识地图]]

## 核心一句话

【必须会】互斥解决“能不能同时做”，同步解决“条件满足后什么时候做”；Lock、Condition、Semaphore 和 CAS 是不同语义的工具，必须围绕业务不变量选择。

## 从共享数据到同步原语

~~~text
多个线程
↓
共享可变资源
↓
读-改-写步骤可能交错
↓
Race Condition：结果依赖不可控时序
↓
识别必须保持一致的Critical Section
↓
用Mutex/Lock保证互斥
或用Condition/Semaphore协调条件
或用CAS原子更新单一状态
↓
保证业务不变量
~~~

count++ 大致包含 read → modify → write。两个线程都读到 0，再各自写 1，就会丢失一次更新。

| 概念 | 关注问题 | 一句话 |
|---|---|---|
| Race Condition | 结果是否依赖并发时序 | 交错后可能得到错误结果 |
| Critical Section | 哪段代码必须整体受保护 | 访问共享不变量的关键区域 |
| Mutual Exclusion | 谁能同时进入 | 不能一起干 |
| Synchronization | 何时允许继续 | 条件满足才能干 |
| Atomicity | 是否暴露中间状态 | 一个操作不可被交错观察 |

## synchronized 与 ReentrantLock

| 维度 | synchronized | ReentrantLock |
|---|---|---|
| 互斥/可重入 | 支持 | 支持 |
| 释放 | 正常/异常退出监视器时自动释放 | 必须 finally 中 unlock |
| 尝试/超时获取 | 不直接提供 tryLock 语义 | tryLock、超时 |
| 可中断获取 | 普通进入监视器不提供同等 API | lockInterruptibly |
| 条件队列 | 每个监视器一组 wait-set 语义 | 一个 Lock 可创建多个 Condition |
| 实现层 | JVM monitor 语义 | java.util.concurrent.locks 显式锁 |

不要机械回答“ReentrantLock 一定更快”。现代 JVM 下性能取决于竞争、临界区和使用方式；通常先按语义选型。

~~~java
lock.lock();
try {
    updateSharedState();
} finally {
    lock.unlock();
}
~~~

## Condition 不是 Lock

Lock 保护互斥；Condition 表达“拿到同步结构后，条件不满足应该等待，条件变化如何通知”。

~~~text
consumer获得lock
↓
队列为空
↓
notEmpty.await()
↓ 释放当前lock并进入Condition等待队列

producer获得lock并放入数据
↓
notEmpty.signal()
↓
consumer从Condition等待转为有资格竞争lock
↓
重新获得lock
↓
重新检查条件后继续
~~~

signal 不等于被唤醒线程立刻执行；它还要重新竞争 Lock。await/wait 通常放在 while 中，因为唤醒、超时、竞争和其他线程消费都可能让条件再次不成立。

~~~java
lock.lock();
try {
    while (queue.isEmpty()) {
        notEmpty.await();
    }
    return queue.remove();
} finally {
    lock.unlock();
}
~~~

对应关系：Object.wait 约等于 Condition.await，notify/notifyAll 约等于 signal/signalAll；Condition 的优势是一个 Lock 可区分 notEmpty、notFull 等多个等待条件。

## Semaphore

Semaphore 用 N 个 permit 表达“最多 N 个执行流同时进入”：

~~~text
任务申请permit
├─ 有permit：减一并进入
└─ 无permit：等待/失败
任务结束
↓
release归还permit
~~~

它适合限制外部 API、连接使用或资源池并发度，但 Semaphore 不是连接池本身；连接的创建、健康检查、复用和回收仍由连接池负责。

## CAS 与 Atomic

~~~text
读取当前值
↓
当前值 == expected ?
├─ 是：以底层原子操作写入newValue
└─ 否：失败，重读/重试/退出
~~~

AtomicInteger、AtomicLong、AtomicReference 提供单个原子操作；CAS 避免了某些阻塞锁，但高竞争自旋会持续消耗 CPU。

### 单个 Atomic 操作不等于整个业务原子

~~~java
if (count.get() > 0) {
    count.decrementAndGet();
}
~~~

交错示例：

~~~text
count = 1
线程A：get()看到1
线程B：get()也看到1
线程A：decrementAndGet() → 0
线程B：decrementAndGet() → -1
~~~

每个方法各自原子，但“判断 + 扣减”不是一个原子整体。可用 compareAndSet 循环实现条件更新，或用锁保护完整业务临界区。

### ABA

~~~text
A读取值100
↓
B把100改为200，再改回100
↓
A的CAS只比较当前值，误以为状态没经历变化
~~~

需要关心变化历史时可引入版本号，Java 可用 AtomicStampedReference。不是所有 CAS 场景都有业务 ABA 风险，先判断状态变化是否影响正确性。

## 死锁、活锁与饥饿

死锁是多个执行流永久等待彼此持有的资源。四个必要条件：

1. **互斥**：资源不能同时共享使用。
2. **请求并保持**：持有已有资源时继续等待新资源。
3. **不可剥夺**：资源不能被系统强行拿走，只能由持有者释放。
4. **循环等待**：A 等 B、B 等 C、C 又等 A。

| 策略 | 核心思路 | 面试边界 |
|---|---|---|
| 预防 | 设计上破坏四条件之一 | 固定加锁顺序最常用 |
| 避免 | 分配前判断是否仍处于安全状态 | 银行家算法；Unsafe 不等于已经 Deadlock |
| 检测 | 允许发生，再检查等待图/资源图 | Java 可看 thread dump 的锁环 |
| 恢复 | 终止、回滚、抢占或人工处置 | 要考虑业务一致性与损失 |

Java 工程优先：固定全局加锁顺序、缩短临界区、避免持锁调用慢 IO、tryLock 超时、finally 释放、监控线程栈。

- Deadlock：彼此等待，整体不再推进。
- Livelock：线程一直让步/重试，状态变化但任务无进展。
- Starvation：某个线程长期拿不到资源，其他线程仍可能推进。

## Java / Linux / SmartRenew 关联

- Java 侧 JMM、volatile、happens-before 和 AQS 继续见 [[java八股文/Java后端完整知识体系/05-JMM并发安全与锁]]；本篇是同步原语的唯一跨层主解释。
- SmartRenew 的 Redis 预占、MySQL 条件更新和唯一约束解决的是跨进程业务不变量，不能只靠当前 JVM 的 synchronized。
- 连接池 20 不应靠创建 10000 个线程“突破”，应让连接池/Semaphore/限流共同表达真实容量。
- Linux/Java 排障先保存线程 dump、锁持有与等待链，再决定重启；重启消除现场但不消除根因。

> [!danger] 高频错误
> - “同步就是加锁”错误：锁偏互斥，Condition/事件还负责条件顺序。
> - “Condition 是另一种 Lock”错误：它必须依附 Lock 表达等待条件。
> - “signal 后线程立刻运行”错误：它还要重新竞争 Lock。
> - “await 用 if 就够了”错误：唤醒不保证条件仍满足，应用 while 重检。
> - “Semaphore 就是连接池”错误：它只表达许可数量。
> - “Atomic 类让整段业务天然原子”错误：多个原子方法仍可交错。
> - “CAS 一定比锁快”错误：高竞争自旋会浪费 CPU。
> - “Unsafe 就是已经死锁”错误：它表示不能保证存在安全完成顺序。

## 高频面试题

### 1. Race Condition 和 Critical Section 是什么？

- **30 秒答案**：竞态指结果依赖并发交错并可能出错；临界区是访问共享不变量、必须整体受保护的代码。先识别临界区，再选择锁、CAS 或线程封闭。
- **追问方向**：count++ 为什么不是原子？临界区越大越好吗？
- **常见错误答案**：只要多线程运行就一定叫竞态。

### 2. 互斥和同步有什么区别？

- **30 秒答案**：互斥回答“谁不能同时进入”，同步回答“条件和顺序满足后谁可以继续”。生产者消费者既要互斥保护队列结构，也要用条件协调空/满。
- **追问方向**：原子性与互斥关系？信号量属于哪类？
- **常见错误答案**：两者都是 synchronized 的同义词。

### 3. synchronized 和 ReentrantLock 如何选？

- **30 秒答案**：两者都互斥且可重入；synchronized 自动释放、语法简单，ReentrantLock 提供 tryLock、超时、可中断和多个 Condition，但必须 finally 解锁。按控制语义选，不机械比较快慢。
- **追问方向**：为什么持锁慢 IO 危险？公平锁有什么代价？
- **常见错误答案**：ReentrantLock 永远更快，所以 synchronized 已过时。

### 4. Condition 和 Lock 是什么关系？

- **30 秒答案**：Lock 管互斥，Condition 是该 Lock 上的条件等待队列。await 会释放 Lock 并等待；signal 只让线程获得重新竞争 Lock 的资格，拿到锁并重检条件后才能继续。
- **追问方向**：为什么用 while？多个 Condition 有何价值？
- **常见错误答案**：Condition 本身可以直接锁住共享数据。

### 5. Semaphore 解决什么问题？

- **30 秒答案**：用 N 个 permit 限制同时进入某资源的执行流数量，适合保护连接、外部 API 或缓冲槽；它不是资源池，不负责资源生命周期。
- **追问方向**：permit 泄漏会怎样？Mutex 与二值信号量区别？
- **常见错误答案**：Semaphore 能自动创建和回收数据库连接。

### 6. CAS 和 AtomicInteger 是什么，代价是什么？

- **30 秒答案**：CAS 原子比较当前值与 expected，相等才写入 newValue；AtomicInteger 用它提供单变量原子更新。失败重试可避免阻塞，但高竞争自旋耗 CPU，还可能遇到 ABA。
- **追问方向**：LongAdder 与 AtomicLong 如何选？CAS 是否无锁无成本？
- **常见错误答案**：CAS 永远成功，而且永远比锁快。

### 7. 为什么 AtomicInteger 不能保证整段业务原子？

- **30 秒答案**：Atomic 只保证某个方法的原子性，判断、读取、更新分成多个调用时，其他线程可在中间插入。应把不变量编码进 CAS 循环，或用锁包住完整临界区。
- **追问方向**：如何实现大于零才扣减？多个字段怎样保持一致？
- **常见错误答案**：变量类型换成 Atomic 后所有 if/else 都线程安全。

### 8. ABA 是什么？

- **30 秒答案**：值从 A 变 B 又回 A，CAS 只看当前值可能误判从未变化。若变化历史影响业务，可用版本戳，如 AtomicStampedReference。
- **追问方向**：哪些场景不关心 ABA？版本号会不会溢出？
- **常见错误答案**：ABA 是 CAS 更新失败。

### 9. 死锁四条件是什么，Java 中如何避免？

- **30 秒答案**：互斥、请求并保持、不可剥夺、循环等待。Java 工程中优先统一加锁顺序、减少嵌套和持锁时间、避免持锁慢 IO、使用超时/可中断获取并通过线程 dump 检查锁环。
- **追问方向**：Unsafe 是否等于死锁？死锁、活锁、饥饿区别？
- **常见错误答案**：加更多锁或捕获异常就能避免死锁。
