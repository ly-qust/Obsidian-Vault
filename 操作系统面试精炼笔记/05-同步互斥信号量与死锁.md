# 同步、互斥、信号量与死锁

> 当前面试主入口：[[操作系统面试精炼笔记/00-操作系统知识地图]]
> 本文讲共享资源的 OS 问题；Java 并发工具选型仍回看既有精炼笔记。

## 一句话结论

互斥保证同一时刻只有一个执行单元进入临界区，同步保证事件或执行顺序满足约束，信号量用计数表达可用资源，错误的循环等待会形成死锁。

## 1. 同步与互斥

- **临界区**：访问共享状态且必须保持一致性的代码区。
- **互斥**：同一时刻最多一个执行单元进入临界区，关注“不能同时做”。
- **同步**：多个执行单元按条件或顺序协作，关注“什么时候可以做”。
- **原子性**：操作不可被观察为中间状态；原子性有助于同步，但不等于完整的互斥协议。

典型因果链：

```text
多个执行单元共享状态
→ 读改写之间可能交错
→ 结果依赖时序，产生竞态
→ 用互斥保护临界区、用同步等待条件
→ 临界区过大或顺序设计错误，吞吐下降甚至死锁
```

## 2. 信号量与互斥量

| 工具 | 核心语义 | 常见用途 |
|---|---|---|
| 互斥量 Mutex | 0/1 所有权，持有者负责释放 | 保护一个临界区 |
| 二值信号量 | 计数为 0/1，强调许可而非严格所有权 | 事件通知或简单互斥 |
| 计数信号量 | 计数代表可用许可，获取减一、释放加一 | 连接池、缓冲区、并发上限 |

信号量不是“自动让代码安全”：它只提供计数和等待/唤醒语义，资源获取、释放和异常路径仍要由程序保证。资源许可数也不能绕过数据库、线程或下游服务真实容量。

## 3. 死锁

死锁是多个执行单元永久等待彼此持有的资源，常见四个必要条件：

1. **互斥**：资源同一时刻只能被一个执行单元占用。
2. **占有且等待**：已拿到资源，同时继续等待其他资源。
3. **不可剥夺**：资源不能被强行拿走，只能由持有者释放。
4. **循环等待**：形成环形等待关系。

预防/降低风险的因果链：

```text
统一资源获取顺序
→ 降低循环等待
设置超时/可中断获取
→ 避免无限等待
缩短临界区并在 finally 释放
→ 减少占有资源的时间
监控线程栈和锁等待
→ 定位实际阻塞链
```

超时和重试只能降低“永久等待”风险，不能自动修复数据一致性；业务重试还要配合幂等和失败补偿。

## 4. Java / Linux 关联

- Java `synchronized`、`ReentrantLock`、并发容器是应用层工具；不要在本篇重复锁实现、CAS、自旋和线程池参数，回看 [[java八股文/Java后端面试精炼笔记/02-并发工具选型]]。
- Java 线程卡在 `BLOCKED`、`WAITING` 或 `TIMED_WAITING` 时，先看线程 dump、锁持有关系、数据库/连接池等待和外部调用。
- Linux 进程/线程同步可能涉及用户态快速路径和内核等待；面试回答到“状态、资源、等待队列和排查方法”即可，不展开 futex 或内核源码。
- 共享内存 IPC 必须额外配同步协议；这也是 [[操作系统面试精炼笔记/02-进程状态与IPC]] 中共享内存的关键边界。

## 容易答错点

- “同步就是加锁”：锁主要解决互斥，同步还包括条件等待、事件通知和先后顺序。
- “信号量等于互斥锁”：计数信号量可以允许多个许可，所有权语义也不同。
- “加锁越多越安全”：锁粒度、顺序和释放路径错误会降低吞吐或造成死锁。
- “死锁和饥饿一样”：死锁是循环等待导致整体无法推进；饥饿是某些执行单元长期得不到资源，原因和处理方式不同。

## 高频追问

1. 如何判断是否死锁？——看多个线程/进程互相持有并等待资源的环，结合线程栈、锁监控和资源调用链。
2. 如何避免死锁？——固定加锁顺序、一次性申请、超时/可中断获取、缩短临界区并保证释放。
3. 生产者消费者为什么适合信号量？——空槽和已有数据分别可用计数表示，再配合互斥保护缓冲区结构。
