# 网络故障排查

> 当前面试主入口：[[计算机网络面试精炼笔记/00-计算机网络知识地图]]

## 一句话结论

网络排障不要从“猜代码”开始，而要沿 DNS → IP/路由 → 端口 → TCP → TLS → HTTP → Nginx/后端日志逐层缩小范围。

## 1. 标准因果链

```text
确认现象和时间范围
→ 确认域名解析结果
→ 确认本机地址、路由、网关和防火墙
→ 确认目标端口是否监听、连接是否建立
→ 分辨 TCP 超时/重置/关闭
→ 分辨 TLS 证书/握手问题
→ 查看 HTTP 状态码、Header 和响应体
→ 查看 Nginx access/error log 与后端服务日志
→ 结合 trace_id、线程池/连接池和下游依赖定位根因
```

## 2. 症状到命令

| 症状 | 优先检查 | 常用工具 |
|---|---|---|
| 域名无法解析 | DNS、缓存、解析器 | `dig`/`nslookup`、`getent hosts` |
| IP 不通 | 地址、路由、网关、防火墙 | `ip addr`、`ip route`、`ping`、`traceroute` |
| 端口拒绝/超时 | 监听、进程、防火墙、安全组 | `ss -lntp`、`lsof -i`、`nc`/`telnet` |
| HTTPS 失败 | 证书、域名、TLS 握手 | `curl -v`、`openssl s_client` |
| HTTP 4xx | 请求、认证、权限、参数 | `curl -i`、Nginx access log、应用日志 |
| HTTP 5xx/502 | 网关、上游服务、连接和超时 | `nginx -t`、`ss`、`curl`、error log、`journalctl` |
| 偶发超时 | 重传、连接池、下游延迟、GC/CPU | `ss -ti`、应用指标、日志、抓包 |

命令是证据收集工具，不是结论本身：`ping` 失败可能是 ICMP 被禁，`ping` 成功也不代表 TCP、TLS 和业务都正常。

## 3. Java / Linux / SmartRenew 关联

- Java 客户端要区分 DNS、connect、TLS、write、read 和总超时，避免只设置一个无限等待；AI HTTP 可靠调用见 [[pyAI应用/day6HTTP 方法、状态码、header、JSON、连接读取超时httpx同步与异步]]。
- Linux 常用 `ip addr`、`ip route`、`ss`、`curl`、`ping`、日志和防火墙命令，基础入口见 [[Linux/命令操作]]、[[Linux/未命名]]。
- Nginx 排障顺序是服务状态 → 配置语法 → 端口监听 → 本机访问 → 日志 → 后端健康，复用 [[nginx/nginx(linux)]] 的运维主线。
- SmartRenew 要沿浏览器/客户端 → Nginx → Java 服务 → MySQL/Redis/MQ/外部服务逐段定位，并用 trace_id、状态码、业务错误码和请求时间串联证据，项目排障见 [[SR/SmartRenew面试精炼笔记/07-面试速记与待验证问题]]。

## 4. 高频面试回答

> 我会先复现并记录时间、请求地址和 trace_id，再按 DNS、路由、端口、TCP、TLS、HTTP、网关和后端依赖分层排查。每一层都用一个可验证的命令或日志证据确认，最后区分网络不可达、服务未监听、协议失败、上游超时和业务错误，而不是把所有问题都归因于“网络不好”。

## 容易答错

- `Connection refused` 和连接超时不同：前者通常更接近主动拒绝/无监听，后者可能是丢包、策略丢弃或路径问题。
- 502、504 不一定是 Nginx 自己故障，常见是上游不可达、响应慢或代理超时。
- `curl localhost` 只验证本机路径，不能证明外部 DNS、网关、防火墙和公网入口正常。
- 只看应用日志可能漏掉 DNS、TLS、Nginx 和内核连接层证据。

## 高频追问

1. 访问域名超时如何排查？——先解析域名，再查路由和端口，随后区分 TCP、TLS、HTTP 和上游处理时间。
2. Nginx 返回 502 怎么办？——看 error log，确认后端进程、监听端口、代理地址、本机 curl 和后端超时。
3. AI API 偶发超时如何定位？——拆分 DNS/connect/TLS/write/read/总耗时，结合重试、连接池、下游限流和 trace_id。
