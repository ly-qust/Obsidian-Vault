# TCP 可靠传输、流量控制与拥塞控制

> 当前面试主入口：[[计算机网络面试精炼笔记/00-计算机网络知识地图]]

## 一句话结论

TCP 用序号、确认、校验和、重传及窗口机制实现可靠有序字节流，流量控制保护接收方，拥塞控制保护网络，两者限制对象不同。

## 1. 可靠传输因果链

```text
发送方给字节编号并放入发送窗口
→ 接收方校验并按序确认
→ 发送方根据 ACK 推进窗口
→ 超时、重复 ACK 或检测到丢包
→ 重传缺失数据并调整发送节奏
→ 接收方按序交付字节流
```

关键点：

- 序号定位字节范围，ACK 告诉发送方接收方期望的下一个序号。
- 校验和发现传输损坏；确认和重传应对丢包。
- TCP 负责字节流可靠性，不知道应用层一条消息的边界，也不保证业务操作已经成功。
- 超时重传和快速重传是不同触发路径；面试说清“什么时候判断丢包、如何降速”即可，不展开具体算法计算。

## 2. 流量控制 vs 拥塞控制

| 机制 | 保护对象 | 核心依据 | 典型问题 |
|---|---|---|---|
| 流量控制 | 接收方 | 接收窗口 `rwnd` | 接收缓冲区快满，发送方要放慢 |
| 拥塞控制 | 网络 | 拥塞窗口 `cwnd`、丢包/RTT等信号 | 中间链路或路由器拥塞，整体要降速 |

实际发送窗口通常受 `min(rwnd, cwnd)` 约束：接收方能接多少和网络当前能承受多少，取更小者。不要把接收窗口和拥塞窗口都说成“服务器 CPU 忙”。

拥塞控制常用概念：慢启动逐步探测容量，拥塞避免更谨慎增长，出现丢包或拥塞信号后降低发送速率；不同版本和实现细节不在本篇展开。

## 3. 高频面试回答

> TCP 可靠传输靠序号、确认、校验和与重传把不可靠网络整理成有序字节流。流量控制通过接收窗口限制发送方，避免接收缓冲区溢出；拥塞控制根据网络反馈调整拥塞窗口，避免把链路和中间设备压垮。最终发送量同时受接收方和网络两端约束。

## 4. Java / Linux / SmartRenew 关联

- Java `Socket` 的输入流是字节流，应用必须自己处理完整消息、长度或分隔符；原始 TCP 流程见 [[java笔记/17网络编程]]。
- Linux 排查重传和连接异常可结合 `ss -s`、`ss -ti`、抓包工具和应用超时日志；命令基础见 [[Linux/命令操作]]。
- AI API 或 SmartRenew 请求超时不一定是 TCP 丢包，也可能是 DNS、TLS、服务端排队、连接池或下游处理慢；HTTP 客户端要设置连接/读取/总超时，参考 [[pyAI应用/day6HTTP 方法、状态码、header、JSON、连接读取超时httpx同步与异步]]。
- SmartRenew 的重试要区分连接失败、响应超时和业务失败，并配合幂等键，避免可靠传输被误解为业务不会重复。

## 容易答错

- TCP 可靠不等于低延迟，也不等于业务层 exactly-once。
- `rwnd` 是接收方通告，`cwnd` 是发送方对网络拥塞的估计，不能混为一谈。
- ACK 到达不等于对端业务已经提交成功，只说明 TCP 层收到相应字节。
- TCP 没有消息边界，不能假设一次 `read` 取到一次完整请求。

## 高频追问

1. TCP 如何发现丢包？——超时、重复 ACK 等信号；发现后重传并降低发送节奏。
2. 为什么发送窗口取两个窗口的较小值？——既不能压垮接收方，也不能超过网络当前承载能力。
3. HTTP 请求超时是不是 TCP 一定重传？——不一定，可能是解析、建连、TLS、服务端处理或读取阶段任一环节超时。
