## 一、它解决什么实际问题？      

ArrayList 的本质是**"会自动扩容的数组"**。

### 原生数组的痛点

```
// 原生数组：大小固定，一旦定死就不能变
String[] arr = new String[10];
arr[10] = "x"; // ArrayIndexOutOfBoundsException
```

你写业务代码时，**几乎永远不知道数据会有多少条**——查数据库可能返回 3 条，也可能返回 3000 条。原生数组要求你提前猜大小，猜错了要么浪费内存，要么直接崩。

### ArrayList 的解法

| 能力            | 实现方式                                                   |
| ------------- | ------------------------------------------------------ |
| **动态扩容**      | 不够了就新建一个 1.5 倍大的数组，把旧数据拷贝过去                            |
| **随机访问 O(1)** | 底层还是数组，`get(i)` 直接算内存偏移量                               |
| **泛型安全**      | 编译期检查类型，不用手动强转                                         |
| **集合框架适配**    | 实现了 List、RandomAccess、Serializable 等接口，能和整个 Java 生态互操作 |

> 类比：ArrayList 就像一个**可伸缩的文件柜抽屉**。东西放满了，它自动买一个更大的抽屉，把所有文件夹搬过去——你只管往里塞，不用操心抽屉够不够大。

## 二、什么场景下会踩坑？

### 坑 1：遍历时删除（最经典）

```
// ❌ 并发修改异常 ConcurrentModificationException
for (String s : list) {
    if (s.equals("bad")) {
        list.remove(s);
    }
}
```

**原因**：增强 for 循环底层是 Iterator，Iterator 有个 `modCount` 计数器。你用 list.remove() 改了 modCount，但 Iterator 不知道，下次 `next()` 时发现对不上就抛异常。

**正确写法**：

```
// ✅ 用 Iterator 自己的 remove
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("bad")) it.remove();
}

// ✅ 或者 Java 8+
list.removeIf(s -> s.equals("bad"));
```

### 坑 2：频繁在头部/中间插入删除

```
// ❌ 每次都要移动后面所有元素，O(n)
for (int i = 0; i < 10000; i++) {
    list.add(0, i); // 每次插入都要把已有元素全部后移一位
}
```

**原因**：数组是连续内存，中间插一个元素，后面所有元素都得往后挪。10000 次插入就是 10000×10000/2 ≈ 5000 万次元素移动。

> 这种场景应该用 **LinkedList**（但注意 LinkedList 也不是万能的，它的随机访问也是 O(n)）。

### 坑 3：扩容导致的性能毛刺

```
// ❌ 不知道最终大小，触发多次扩容拷贝
List<Integer> list = new ArrayList<>(); // 默认容量 10
for (int i = 0; i < 1000000; i++) {
    list.add(i); // 会触发约 10→15→22→33→...→约150万 十几次扩容
}
```

**原因**：每次扩容都要 `Arrays.copyOf()`，把整个数组重新拷贝一遍。数据量大时，这是不可忽视的开销。

**优化**：

```
// ✅ 预估容量，一次性分配
List<Integer> list = new ArrayList<>(1000000);
```

### 坑 4：`Arrays.asList()` 返回的假 ArrayList

```
// ❌ 这不是 java.util.ArrayList！
List<String> list = Arrays.asList("a", "b", "c");
list.add("d"); // UnsupportedOperationException
```

**原因**：`Arrays.asList()` 返回的是 `Arrays` 内部的 `ArrayList` 类，它**不支持 add/remove**，大小固定。很多人被名字骗了。

**正确写法**：

```
// ✅ 包一层真正的 ArrayList
List<String> list = new ArrayList<>(Arrays.asList("a", "b", "c"));
```

### 坑 5：subList 内存泄漏

```
// ❌ subList 持有原 list 的引用，原 list 无法被 GC
List<String> big = new ArrayList<>(Collections.nCopies(1000000, "x"));
List<String> small = big.subList(0, 10);
// big 看起来不用了，但因为 small 引用着它，100万元素全占着内存
```

**原因**：`subList()` 返回的是原 list 的**视图**，不是新 list。它内部持有原 list 的引用。

**正确写法**：

```
// ✅ 新建一个独立的 list
List<String> small = new ArrayList<>(big.subList(0, 10));
```

### 坑 6：非线程安全

```
// ❌ 多线程同时 add，可能丢数据、数组越界、size 不一致
// 因为 add 不是原子操作：检查容量 → 赋值 → size++
```

多线程场景用 `CopyOnWriteArrayList`（读多写少）或 `Collections.synchronizedList()`，或者用并发队列。

## 三、如果让我设计一个替代方案，我会怎么改？

这是面试的**开放题**，考察你对数据结构的理解深度。我会从以下几个角度思考：

### 方案 A：分块数组（Unrolled Linked List / Chunked Array）

**核心思路**：不搞一个大数组，而是搞一个**数组的数组**——每块固定大小（比如 1024），块之间用链表或数组索引连接。

```
块1[1024个元素] → 块2[1024个元素] → 块3[1024个元素] → ...
```

**改进点**：

- **扩容不再全量拷贝**：满了就新加一个块，O(1) 完成
- **头部插入不再全量移动**：如果当前块有空间，只挪当前块的元素
- **内存更友好**：不会因为一次扩容申请一大片连续内存

**代价**：随机访问从纯 O(1) 变成 O(1) 常数变大（先算第几块，再算块内偏移），但仍然是常数级。

> 这其实就是 **C++ deque** 的设计思路，也是很多高性能语言动态数组的演进方向。

### 方案 B：持久化/不可变数组（Persistent Vector）

**核心思路**：借鉴 Clojure 的 PersistentVector，用**树状结构**（32 叉树）存储，修改时只复制路径上的节点。

**改进点**：

- **写操作不影响旧版本**：天然线程安全，不需要加锁
- **适合函数式编程和并发场景**

**代价**：读操作需要树的遍历，常数比纯数组大。

### 方案 C：自适应结构（根据操作模式自动切换）

**核心思路**：内部维护一个"操作画像"——如果检测到大量头部插入，自动切换到链表或分块结构；如果检测到大量随机访问，维持数组结构。

**改进点**：对使用者透明，自动适配访问模式。

**代价**：实现复杂度极高，切换本身有开销，且"检测"可能误判。

### 方案 D：我个人最推荐的务实改进

如果让我在工程上做一个 ArrayList 的替代，我会选**方案 A（分块数组）+ 以下优化**：

1. **默认容量策略优化**：不是固定 10，而是根据首次 add 的元素类型/数量做启发式预估
2. **缩容机制**：当前 ArrayList 只扩不缩，`remove` 后内存不释放。我会加一个"使用率低于 25% 时缩容到 1.5 倍实际大小"的策略（类似 C++ vector 的 shrink_to_fit，但自动触发）
3. **批量操作优化**：`addAll` 时直接按目标大小一次性扩容，而不是逐个 add 触发多次扩容
4. **空集合共享**：`new ArrayList<>()` 时共享同一个空数组（JDK 7 已经做了），但进一步可以让小容量 list 共享只读前缀

## 面试回答的黄金结构

被问到这个问题时，按这个顺序答最加分：

1. **一句话定位**：ArrayList 是动态数组，解决原生数组大小固定的问题
2. **核心机制**：底层 Object[]，1.5 倍扩容，Arrays.copyOf 拷贝
3. **踩坑场景**：举 2-3 个最典型的（遍历时删除、头部插入、扩容性能、Arrays.asList 陷阱）
4. **替代方案**：体现你思考过数据结构 trade-off，分块数组是最安全、最能体现深度的答案

> 记住：面试官问"你会怎么设计替代方案"，**不是要你真的造一个比 JDK 更好的轮子**，而是看你能不能说出"当前设计的 trade-off 是什么，以及如果改变某个约束条件，结构应该怎么变"。能讲清楚这个，就赢了。








1. ArrayList 底层结构是什么，随机访问为什么快？
ArrayList 底层是`Object[] elementData`对象数组，用来存放集合元素；`size`记录集合实际元素个数，区分数组容量 capacity。 数组内存连续，通过索引直接计算内存偏移地址，不需要遍历，所以随机访问是 O (1) 速度。

2. add 触发扩容的大致过程是什么？
add 添加元素时，会执行`ensureCapacityInternal()`判断是否需要扩容。容量不足进入`grow()`，先计算新容量 = 旧容量的 1.5 倍；如果 1.5 倍仍然小于需要的最小容量，则直接使用最小需要容量。之后开辟新数组，通过`Arrays.copyOf`拷贝旧数组全部元素，把 elementData 引用指向新数组，完成扩容。

3. 中间位置插入和删除为什么是 O (n)？
数组是连续内存结构，在中间插入 / 删除元素，需要调用`System.arraycopy`把该位置之后所有元素整体向后 / 向前平移。最坏在头部操作，移动全部 n 个元素，时间复杂度 O (n)。

4. ArrayList 为什么不是线程安全的？
add 操作`elementData[size++] = e`不是原子操作，拆分为数组赋值、size 自增两步。多线程并发写时，会出现元素覆盖丢失、size 计数错误、数组越界异常，没有加同步保护，因此线程不安全。
