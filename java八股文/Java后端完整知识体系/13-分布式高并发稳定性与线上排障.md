# 分布式、高并发、稳定性与线上排障

## 一句话结论

高并发设计不是堆 Redis、MQ 和线程，而是先确定容量与正确性，再通过缓存、异步、隔离和降级控制资源，最后用可观测证据验证。

## 一、先建立容量模型

至少明确：

- 峰值 QPS 和突发持续时间。
- 请求读写比例。
- 单次请求数据库/缓存/外部调用次数。
- 平均与 P95/P99 延迟。
- CPU、内存、网络、连接池和线程池上限。
- 可接受失败率、恢复时间和数据丢失窗口。

Little's Law 的直观关系：系统内平均并发约等于吞吐乘平均停留时间。下游变慢会使在途请求增加，继续占用线程、连接和内存，形成级联故障。

## 二、高并发四条主线

### 减少工作

索引、缓存、批量、预计算、避免 N+1、减少序列化和重复查询。

### 并行与异步

并行只适合独立工作；异步把等待从请求链移出，但增加状态、重试、顺序和幂等复杂度。

### 限制资源

有界线程池、连接池、队列、Semaphore、限流、单请求大小和超时。

### 故障隔离

按依赖/业务拆线程池和连接池，熔断慢下游，降级非核心功能，防止一个故障拖垮全部。

## 三、限流

| 算法 | 特点 | 边界 |
|---|---|---|
| 固定窗口 | 简单 | 边界突刺 |
| 滑动窗口 | 更平滑 | 统计成本更高 |
| 漏桶 | 匀速输出 | 突发可能排队/拒绝 |
| 令牌桶 | 允许一定突发 | 需合理设置速率与桶容量 |

限流维度：用户、IP、租户、接口、业务资源、下游依赖。返回明确错误码和 Retry-After/降级信息，不能静默超时。

单机限流保护单实例，分布式限流需要共享状态或网关协调，但共享存储本身也是依赖。

## 四、超时、重试、熔断、降级

- 超时：给等待设上限，最好传播整体 deadline。
- 重试：只对可恢复错误，有限次数、指数退避、随机抖动、幂等保护。
- 熔断：失败/慢调用达到阈值时快速失败，给下游恢复窗口。
- 降级：返回缓存、简化结果、关闭非核心能力或转人工。

危险组合：每层各重试 3 次，三层嵌套可能放大为 27 次请求。明确只有哪一层负责重试。

## 五、接口幂等

场景：客户端超时重发、网关重试、MQ 重投、定时补偿、用户重复点击。

设计：

```text
请求携带幂等键
→ 数据库唯一约束抢占
→ 首次执行保存状态/结果
→ 重复请求查询并返回相同结果
→ 失败状态允许受控重试
```

只用 Redis `SETNX` 可能因过期、故障或数据库事务失败留下边界，核心业务仍需数据库约束。

## 六、分布式一致性选择

- 强一致本地事务：同一数据库内优先。
- Outbox/事务消息：跨数据库与 MQ 的最终一致。
- Saga/补偿：长事务拆成本地步骤，每步有补偿语义。
- TCC：Try/Confirm/Cancel，业务侵入和资源预留成本高。
- 两阶段提交：协调成本和可用性边界明显，不是默认答案。

先问业务能否接受最终一致，再选复杂方案。不要为了“分布式”而分布式。

## 七、服务拆分边界

按业务能力、数据所有权和团队协作拆分，不按 Controller/Service/Mapper 技术层拆微服务。

拆分代价：网络失败、数据一致性、链路追踪、部署、测试、版本兼容和运维成本。单体模块化能解决时，不必急于微服务化。

## 八、API 设计

- 请求/响应 DTO 稳定，字段增加保持向后兼容。
- 统一错误码、trace_id、分页和时间格式。
- 写接口定义幂等与冲突语义。
- 超时和重试契约写清楚。
- 批量接口限制元素数和请求体大小。
- 版本演进避免直接删除/改义已发布字段。

## 九、可观测性

### Metrics

请求量、错误率、延迟分位数、资源饱和度；线程池、连接池、队列、缓存命中、MQ 积压、GC。

### Logs

结构化记录时间、级别、服务、trace_id、业务 ID、错误码和异常链。避免记录 Token、密码、身份证、完整请求体等敏感信息。

### Traces

展示请求跨服务和依赖的耗时路径，帮助区分自身处理、数据库、缓存、MQ 和第三方延迟。

完整入口：[[监控/可观测性面试基础]]。

## 十、通用排障顺序

```text
确认影响范围和时间
→ 看变更/发布/流量
→ 看入口RED指标
→ 沿trace找慢节点
→ 看线程池/连接池/队列
→ 看JVM/CPU/内存/GC
→ 看数据库/缓存/MQ/网络
→ 保存证据并止损
→ 修复、验证、复盘
```

RED：Rate、Errors、Duration。资源侧可看 USE：Utilization、Saturation、Errors。

## 十一、典型故障

### 接口突然变慢

检查流量、错误、P99、线程池队列、连接池等待、慢 SQL、外部调用、GC 和网络。先找排队点。

### CPU 高

区分用户态/系统态，定位高 CPU 线程，结合线程栈与 profiler 判断死循环、热点计算、锁自旋、序列化或 GC。

### 内存持续上涨

区分堆、直接内存、线程栈、page cache；看 GC 后基线、对象增长、队列、缓存和 ThreadLocal。

### 数据库连接池耗尽

看获取连接耗时、活跃连接、事务时长、慢 SQL、泄漏和下游等待；不要只增大池。

### Redis 热 Key

看命令 QPS、Key 分布、CPU/网络、Value 大小；本地缓存、拆 Key、限流或读副本都要考虑一致性。

### MQ 积压

看生产速率、消费速率、未确认数、失败重试、单条耗时和下游；扩消费者前确认分区/队列和数据库容量。

## 十二、Linux/网络/容器主线

- Linux：进程、线程、FD、CPU、内存、磁盘、日志、权限。
- 网络：DNS、TCP、TLS、HTTP、NAT、网关、超时。
- Docker：镜像、容器、Volume、网络、资源限制、健康检查。
- Nginx：反向代理、负载均衡、WebSocket、访问/错误日志、504。

## 十三、性能优化原则

1. 先定义指标和基线。
2. 找最大瓶颈，不平均用力。
3. 优先减少无效工作，再考虑并行和硬件。
4. 每次只改可验证因素。
5. 关注 P95/P99、错误率和资源成本，不只看平均值。
6. 负载测试必须接近真实数据分布和依赖容量。
