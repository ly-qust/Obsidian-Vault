# 线程池、异步编程与 Java 21 虚拟线程

## 一句话结论

线程池用于控制昂贵平台线程和任务积压，虚拟线程用于降低“等待型并发任务”的线程承载成本；两者都不能突破数据库连接、CPU、内存和下游容量。

## 一、线程池解决什么

- 复用平台线程，减少创建销毁成本。
- 限制并发，保护 CPU、内存和下游。
- 用队列吸收可控的短时突发。
- 通过拒绝策略明确过载行为。
- 提供任务统计、隔离、命名和关闭管理。

不要只回答“提高性能”。线程池最核心的工程价值是资源治理与过载控制。

## 二、ThreadPoolExecutor 七参数

| 参数 | 作用 | 面试关注 |
|---|---|---|
| corePoolSize | 常态工作线程 | 不等于启动时一定已创建 |
| maximumPoolSize | 最大平台线程 | 只有特定队列策略下才有扩容空间 |
| keepAliveTime | 非核心空闲回收时间 | 可配置核心线程超时 |
| unit | 时间单位 | 与 keepAliveTime 配套 |
| workQueue | 等待队列 | 是否有界决定内存和扩容行为 |
| threadFactory | 创建线程 | 命名、异常、上下文、守护属性 |
| handler | 拒绝策略 | 过载时丢弃、抛错、回压还是记录 |

## 三、任务进入顺序

```text
任务提交
→ 工作线程少于 core：创建核心线程
→ 否则尝试入队
→ 队列满且线程少于 max：创建非核心线程
→ 队列满且线程达到 max：执行拒绝策略
```

因此，无界队列可能让 maximumPoolSize 基本失去扩容意义，并把过载转换成队列延迟和内存风险。

## 四、队列和拒绝策略

### 队列

- ArrayBlockingQueue：有界，容量明确，适合做背压。
- LinkedBlockingQueue：可有界；不设时容量很大，容易积压。
- SynchronousQueue：不保存任务，直接交接，常配合更高最大线程数。
- PriorityBlockingQueue：按优先级处理，但必须防止低优先级饥饿。

### 拒绝策略

- AbortPolicy：抛异常，失败显式，常作为默认安全选择。
- CallerRunsPolicy：调用线程执行，形成一定回压，但可能拖慢上游甚至阻塞关键线程。
- DiscardPolicy：静默丢弃，业务任务通常危险。
- DiscardOldestPolicy：丢最旧任务，可能破坏顺序和业务语义。

关键任务不能只放进 JVM 内存队列；需要 MQ 或持久化任务表、重试、幂等和告警。

## 五、线程数估算

CPU 密集：接近 CPU 核数，需考虑容器 CPU 配额。

等待型任务可用粗略关系：

```text
线程数 ≈ CPU核数 × 目标利用率 × (1 + 等待时间/计算时间)
```

这只是起点。最终要结合响应时间、队列长度、拒绝数、CPU、连接池和下游限额压测。

线程池并发不能大于下游可承受并发。100 个业务线程争 20 个数据库连接，只会在连接池继续排队。

## 六、线程池隔离

不同风险任务使用不同执行器：

- HTTP 请求业务。
- 慢第三方调用。
- 批处理。
- MQ 消费。
- 定时任务。

否则一个下游变慢可能占满共享线程池，拖垮无关接口。隔离后仍要统一监控活跃线程、队列、拒绝、执行时间和异常。

## 七、ExecutorService 生命周期

- `shutdown()`：停止接收新任务，等待已提交任务。
- `shutdownNow()`：尝试中断并返回未开始任务，不保证任务立即停止。
- 任务应正确响应中断，捕获 `InterruptedException` 后通常恢复中断标志或向上抛出。
- 应用优雅停机要协调 Web 接流、线程池、MQ 消费和数据库事务。

## 八、CompletableFuture

它用于组织异步阶段和结果依赖，不等于自动提高吞吐。

```java
CompletableFuture<User> userFuture =
    CompletableFuture.supplyAsync(() -> loadUser(id), ioExecutor);

CompletableFuture<List<Order>> orderFuture =
    CompletableFuture.supplyAsync(() -> loadOrders(id), ioExecutor);

return userFuture.thenCombine(orderFuture, UserProfile::new)
    .orTimeout(800, TimeUnit.MILLISECONDS)
    .exceptionally(ex -> fallback(id));
```

边界：

- 明确指定 Executor，避免阻塞任务占用公共 ForkJoinPool。
- `thenApply` 转换值；`thenCompose` 扁平化嵌套异步；`thenCombine` 合并独立结果。
- 异常可能被包装在 CompletionException 中，保留原 cause。
- 超时只控制等待结果，不一定能真正取消底层网络请求。
- trace_id、SecurityContext、事务上下文不会自动正确跨线程传播。

## 九、Java 21 虚拟线程：工程入口

Virtual Thread、Carrier/Platform Thread、OS Thread、底层 IO、pinning、Spring Boot 配置和 AI/SmartRenew 边界统一见 [[操作系统面试精炼笔记/07-Java21虚拟线程与IO]]，这里不重复调度原理。

Java 工程只保留选择结论：

- 大量独立、结构清晰、主要等待网络/文件/JDBC 的任务：评估 one task → one virtual thread。
- CPU 密集任务：仍用按 CPU 容量控制的执行器。
- 数据库、HTTP、Redis 和第三方 API：仍用连接池、Semaphore、限流与超时。
- ThreadLocal：虚拟线程支持，但每线程大对象会放大堆占用。
- 迁移验证：比较吞吐、P95/P99、CPU、内存、连接等待、pinning 和失败率，不只比较线程数。

Java 21 API 代码、卸载链和 Spring Boot 开关只在主解释位置维护，避免本篇与 OS 专题产生两个版本。

## 十、平台线程池与虚拟线程如何选

| 场景 | 建议 |
|---|---|
| CPU 密集计算 | 有界平台线程池，接近可用 CPU |
| 大量独立阻塞 IO | 评估虚拟线程，一任务一线程 |
| 必须限制第三方并发 | 无论哪种线程都配 Semaphore/连接池/限流 |
| 长生命周期事件循环 | 根据框架模型使用平台线程/事件循环 |
| 关键可靠任务 | MQ/任务表持久化，线程只负责执行 |

## 十一、排障指标

- 平台线程池：pool size、active、queue size、completed、reject。
- 任务：排队时间、执行时间、超时、取消和异常。
- 虚拟线程：创建速率、等待点、载体利用、pinning、下游连接等待。
- 系统：CPU、内存、GC、线程数、FD、网络和连接池。
