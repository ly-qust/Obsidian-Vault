# JVM 内存、类加载、GC 与调优

## 一句话结论

JVM 面试要从“类怎么进入、对象怎么创建、引用怎么可达、内存怎么回收、故障怎么取证”形成闭环，而不是只背内存区名称。

## 一、运行时内存视角

| 区域 | 线程关系 | 主要内容 | 常见问题 |
|---|---|---|---|
| 程序计数器 | 私有 | 当前字节码执行位置 | 通常不讨论 OOM |
| Java 虚拟机栈 | 私有 | 栈帧、局部变量、操作数栈 | StackOverflowError、线程过多 |
| 本地方法栈 | 私有/实现相关 | native 调用 | 本地栈与线程问题 |
| 堆 | 共享 | 对象和数组 | Java heap space、GC 压力 |
| 方法区/元空间实现 | 共享 | 类元数据、运行时常量等 | Metaspace OOM、类加载泄漏 |
| 直接内存 | 堆外 | NIO Buffer 等 | Direct buffer memory |

“对象都在堆上”是概念化说法；JIT 可能通过逃逸分析进行标量替换等优化，但排障仍应以可观测事实为准。

## 二、对象创建链

```text
执行 new
→ 检查类是否已加载/初始化
→ 分配内存
→ 零值初始化
→ 设置对象头
→ 执行字段初始化与构造器
→ 引用返回调用方
```

分配可采用指针碰撞或空闲列表，线程局部分配缓冲 TLAB 用于减少多线程分配竞争。对象头通常含运行时标记、类型信息等；具体布局受 JVM、压缩指针和对象状态影响。

## 三、引用与可达性

GC Roots 常见来源：线程栈活动引用、静态字段、JNI 引用、同步监视器等。

可达性分析从 Roots 遍历对象图，不可达对象才具备被回收条件。

引用类型：

- 强引用：通常只要可达就不回收。
- 软引用：内存压力下可能回收，不应用作精确缓存策略。
- 弱引用：下一次回收时更容易清理，WeakHashMap 等场景。
- 虚引用：配合 ReferenceQueue 跟踪回收后处理，不提供普通对象访问。

## 四、类加载生命周期

```text
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
```

- 加载：获得字节流并创建 Class 元数据。
- 验证：保证格式和字节码安全。
- 准备：为静态字段分配并设置初始零值（常量等有特殊规则）。
- 解析：符号引用转换为直接引用，可按实现延后。
- 初始化：执行类初始化方法，完成静态字段显式赋值和静态块。

## 五、双亲委派

类加载器通常先委托父加载器尝试，父无法加载再由自己加载。价值：避免核心类被应用随意替换、提高类复用和安全边界。

边界：SPI、应用服务器、插件系统等可能需要线程上下文类加载器或自定义委派模型。不要回答成“任何类加载都严格不能打破双亲委派”。

类身份由“类全名 + 定义它的 ClassLoader”共同决定；同名类由不同加载器定义时也可能不能互相转换。

## 六、垃圾判断与基本算法

- 标记-清除：标记存活后清理，可能产生碎片。
- 标记-复制：把存活对象复制到另一空间，分配快但需额外空间。
- 标记-整理：存活对象向一端移动，减少碎片但整理成本高。
- 分代收集：利用多数对象朝生夕死、部分长期存活的经验进行区域化处理。

现代收集器是这些思想和并发、区域化、写屏障等机制的组合，不应只背一个算法名称。

## 七、常见收集器认知

| 收集器 | 目标特征 | 回答重点 |
|---|---|---|
| Serial | 单线程、简单 | 小堆或特定客户端场景 |
| Parallel GC | 吞吐优先 | 批处理与吞吐，停顿相对集中 |
| G1 | 分区、可预测停顿目标 | Java 21 常见默认选择，平衡吞吐与停顿 |
| ZGC | 低停顿、并发 | 大堆低停顿，需结合版本与工作负载验证 |

不要说某个收集器“最好”。选择取决于延迟目标、吞吐、堆大小、CPU、对象分配和版本。

## 八、Minor/Major/Full GC

这些术语在不同收集器和日志中含义可能不同。面试时应结合实际 GC 日志说明收集范围、触发原因、停顿和回收效果，不把“Full GC”简单等同于“整个 JVM 停很久且一定回收所有对象”。

## 九、内存泄漏与内存溢出

- 内存泄漏：不再有业务价值的对象仍被引用，不能回收。
- 内存溢出：申请资源超过可用上限；可能由泄漏、容量不足、突发流量或大对象导致。

常见泄漏源：静态集合、无上限缓存、ThreadLocal 未清理、监听器未注销、ClassLoader 引用、队列积压。

## 十、OOM 分类与取证

### Java heap space

保存 heap dump，查看大对象、支配树、引用链和增长趋势。不要只增大 `-Xmx`。

### Metaspace

检查动态类生成、热部署、ClassLoader 无法卸载和类数量。

### Direct buffer memory

检查 NIO 直接缓冲、网络框架池化、显式上限和 native memory。

### Unable to create native thread

检查进程线程数、栈大小、系统限制、虚拟内存和线程泄漏。

## 十一、CPU 高与线程问题

```text
确认进程CPU
→ 找高CPU线程
→ 把线程ID转换为线程dump格式
→ 对照栈定位热点方法/自旋/死循环
→ 结合JFR、指标和代码验证
```

常用证据：`top -H`、`jcmd`、`jstack`、JFR、async-profiler。工具使用要匹配生产权限和性能影响。

## 十二、GC 日志怎么看

至少关注：

- GC 原因与收集器。
- GC 前后堆占用和回收量。
- 停顿时间及分位数。
- 分配速率、晋升速率。
- Full GC 是否频繁、回收后基线是否持续升高。
- 应用延迟是否与 GC 时间线相关。

一次 GC 长不一定是根因，频率、业务时间线和回收效果同样重要。

## 十三、调优顺序

1. 明确延迟、吞吐、成本目标。
2. 保存 GC 日志、JFR、线程 dump、heap dump 等证据。
3. 先修对象泄漏、无界队列、大对象和低效代码。
4. 再调整堆、线程栈、收集器和停顿目标。
5. 压测并对比修改前后，不凭经验宣布优化成功。
