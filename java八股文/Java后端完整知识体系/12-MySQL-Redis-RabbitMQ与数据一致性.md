# MySQL、Redis、RabbitMQ 与数据一致性

## 一句话结论

MySQL 保存业务事实，Redis 加速或协调，RabbitMQ 解耦并异步传递事件；跨组件无法靠一个本地事务自动保证原子，必须设计幂等、重试、补偿和对账。

## 一、数据职责先分清

| 组件 | 主要职责 | 不应承担 |
|---|---|---|
| MySQL/InnoDB | 持久事实、事务、约束、条件更新 | 高吞吐临时缓存 |
| Redis | 缓存、计数、集合计算、短期状态 | 唯一业务事实与绝对正确性 |
| RabbitMQ | 异步解耦、缓冲、重试链路 | 业务幂等和最终事实判断 |

系统正确性应落在数据库约束和状态机上，中间件用于性能、可用性和解耦。

## 二、MySQL Java 后端主线

```text
请求SQL
→ Server层连接/解析/优化
→ 执行计划
→ InnoDB Buffer Pool/索引
→ MVCC或锁
→ redo/undo/binlog
→ 提交或回滚
```

### 索引

- B+Tree 通过有序多路结构减少磁盘页访问，叶子层支持范围扫描。
- 聚簇索引叶子保存整行；二级索引叶子通常保存索引列和主键，因此可能回表。
- 联合索引按定义顺序排序；能否使用取决于条件、范围、排序和优化器成本。
- 覆盖索引减少回表，但索引过宽会增加写放大、缓存占用和维护成本。
- 最终用 EXPLAIN 与实际执行统计验证，不靠“最左匹配口诀”替代分析。

### 事务与 MVCC

- undo 支持回滚和历史版本。
- Read View 决定快照读可见性。
- 当前读和写操作需要锁保护最新数据。
- 隔离级别解决的现象不同；MySQL 默认配置和具体 SQL 语义需结合版本验证。

### 锁与死锁

- 记录锁保护索引记录。
- 间隙/临键锁用于特定隔离与范围场景，范围取决于索引访问路径。
- 未命中合适索引会扫描并锁更多记录，放大竞争。
- 死锁应分析数据库死锁日志、事务顺序和索引，不只是无限重试。

## 三、数据库并发防线

从外到内：

```text
参数校验
→ 业务状态校验
→ 事务
→ 条件更新/行锁
→ 唯一约束
→ 受影响行数判断
```

示例：扣减额度不能先查后改而不加保护。

```sql
UPDATE quota
SET available = available - :amount
WHERE id = :id
  AND available >= :amount;
```

受影响行数为 0 表示条件不成立或并发竞争失败。数据库条件更新是最终防线，Redis 预占只能降低压力。

## 四、Redis 缓存主线

### Cache Aside

```text
读：查缓存 → miss查数据库 → 回填缓存
写：更新数据库 → 删除缓存
```

仍有并发窗口：旧读可能在删除后回填旧值。根据一致性要求可结合延迟双删、消息失效、版本号、短 TTL、订阅 binlog 或直接绕过缓存；没有零成本完美方案。

### 穿透、击穿、雪崩

- 穿透：请求不存在数据；校验、空值缓存、布隆过滤、限流。
- 击穿：热点 Key 失效瞬间大量回源；互斥重建、逻辑过期、预热。
- 雪崩：大量 Key 同时失效或 Redis 故障；随机 TTL、限流降级、高可用和数据库保护。

## 五、Redis 分布式锁

基础正确姿势：

```text
SET key uniqueValue NX PX ttl
释放时Lua比较value后DEL
```

边界：

- 业务执行超过 TTL，需要续期或业务兜底。
- JVM 暂停、网络分区、主从切换可能破坏预期互斥。
- 锁解决“尽量互斥”，数据库唯一约束/条件更新解决最终正确性。
- Key 粒度过大导致吞吐低，过小则无法保护同一业务资源。

## 六、Redis 数据结构选型

| 需求 | 结构 | 边界 |
|---|---|---|
| 对象/计数/位图 | String | 大 Value 与序列化成本 |
| 对象字段 | Hash | 小对象编码与字段更新 |
| 队列/时间线 | List/Stream | 可靠消费优先 Stream/MQ |
| 去重/关系 | Set | 无序、内存成本 |
| 排行/延迟索引 | ZSet | score 精度与热 Key |
| 附近位置 | GEO | 不是完整 GIS |
| UV 估算 | HyperLogLog | 近似，不能列出成员 |

## 七、RabbitMQ 主链

```text
业务事务/Outbox
→ Producer publish
→ Exchange
→ Routing Key + Binding
→ Queue
→ Consumer
→ 业务事务/Inbox
→ ACK
```

三个确认边界：

- Publisher Confirm：Broker 是否接受 publish。
- Return：消息是否无法路由到 Queue。
- Consumer ACK：当前 delivery 是否完成消费确认。

三者不能互相替代。

## 八、为什么消息会重复

业务事务成功后、ACK 前消费者宕机，Broker 不知道业务已成功，会重投。网络超时也可能让发送方不知道 Broker 是否已接受消息而重发。

因此“至少一次”意味着消费者必须幂等。ACK 不是业务幂等机制。

## 九、幂等设计

可组合手段：

- 幂等键/请求号。
- 数据库唯一约束。
- Inbox 消费记录。
- 状态机只允许合法迁移。
- `UPDATE ... WHERE status = expected` 条件更新。
- 返回已经完成的结果，而不是重复执行副作用。

幂等不是“把请求过滤掉”这么简单，还要定义重复请求返回什么、失败后能否重试、幂等记录保存多久。

## 十、数据库与 MQ 双写

错误链路：先更新数据库再直接发送 MQ；在两者之间宕机会产生数据已提交但消息缺失。

Outbox 思路：

```text
同一个数据库事务：更新业务表 + 写Outbox(PENDING)
→ 事务提交
→ 后台发送Outbox
→ Confirm后标记SENT
→ 失败重试
```

它把“跨系统原子问题”转换为“同库事务 + 可重试投递”。仍需处理重复发送、租约、扫描并发、消息顺序、长期失败和对账。

## 十一、消费失败与重试

- 瞬时失败：有限次数退避重试。
- 业务不可重试：直接隔离/死信，避免毒消息堵塞。
- Retry Queue：用 TTL + DLX 等机制延迟回主链。
- DLQ：隔离区，不是自动修复；需要告警、查询、修复和受控重放。
- 重试必须配合幂等，否则“提高成功率”会变成“重复副作用”。

## 十二、最终一致性闭环

```text
状态机 + 数据库约束
→ Outbox保证事件最终可发送
→ MQ至少一次传递
→ Inbox/幂等保证可重复消费
→ 重试/补偿处理瞬时失败
→ 对账发现沉默错误
→ 告警和人工修复兜底
```

最终一致不是“过一会儿自然一致”，必须说明谁重试、重试到何时、如何发现永久失败。
