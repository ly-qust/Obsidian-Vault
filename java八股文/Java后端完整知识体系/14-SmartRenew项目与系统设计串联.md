# SmartRenew 项目与系统设计串联

## 一句话结论

项目面试的高分答案不是罗列 Spring、Redis、RabbitMQ，而是围绕业务正确性说明每个组件为什么存在、代码证据在哪里、还剩哪些失败窗口。

## 一、项目总链路

```text
用户登录
→ JWT认证与授权
→ 提交补贴申请
→ 业务表与Outbox同库事务
→ RabbitMQ投递审核事件
→ Inbox去重并创建审核任务
→ 审核通过
→ Redis预占额度
→ MySQL条件扣减
→ 创建Voucher
→ 商户验券
→ 幂等核销
```

主入口：[[SR/SmartRenew面试精炼笔记/00-SmartRenew项目知识地图]]。

## 二、30 秒项目介绍

> SmartRenew 是围绕补贴申请、审核、发券和商户核销构建的 Java 后端项目。项目重点不是普通 CRUD，而是申请去重、数据库与消息双写、额度并发控制和核销幂等。我使用 Spring 事务和数据库约束保证本地正确性，用 Outbox/Inbox 与 RabbitMQ 处理可靠异步链路，并通过 Redis 预占降低热点额度竞争，最终仍由 MySQL 条件更新和状态机兜底。

只说已在代码或实验中验证的内容；不要把设计方案说成已上线能力。

## 三、分层与职责

| 层 | 主要职责 | 不应承担 |
|---|---|---|
| Controller | HTTP、DTO、校验、身份入口 | 复杂事务与 SQL |
| Service | 业务状态机、事务编排 | 拼接响应协议细节 |
| Mapper/Repository | 数据访问 | 决定完整业务流程 |
| Domain/Model | 状态与不变量 | 依赖 Web 框架 |
| Infrastructure | Redis、MQ、外部服务 | 隐藏失败而返回成功 |

## 四、JWT 请求链

回答顺序：凭证提取 → 签名/过期验证 → Authentication → SecurityContext → 角色授权 → 资源归属校验。

容易漏掉：管理员/商户角色只是一层权限，还要校验商户是否拥有目标 Voucher；日志不记录完整 Token。

详细：[[SR/SmartRenew面试精炼笔记/02-Security与JWT请求链]]。

## 五、申请提交与 Outbox

问题：更新申请状态和发送 MQ 属于两个系统，直接双写存在宕机窗口。

方案：

```text
同库事务
├─ 校验申请状态
├─ 更新申请
└─ 插入Outbox PENDING
提交后发送/定时扫描
→ Confirm成功标记SENT
→ 失败保留并重试
```

证据点：事务边界、Outbox 表字段、唯一约束、扫描条件、租约/重试、Confirm 回调。

剩余风险：重复发送、扫描器并发、发送成功但状态更新失败、消息长期失败。解决依赖幂等、租约、重试、告警和对账。

## 六、消费者与 Inbox

问题：消费者业务提交后 ACK 前宕机会导致 RabbitMQ 重投。

方案：以消息 ID/业务键写 Inbox 或使用业务唯一约束，重复消息返回已有结果；业务事务成功后再 ACK。

不要说“手动 ACK 保证不重复”，ACK 只告诉 Broker 当前 delivery 已处理。

## 七、额度预占

Redis 预占用于降低热点竞争和快速失败，但最终额度由 MySQL 事实源决定。

完整防线：

```text
Redis原子预筛选
→ MySQL条件更新 available >= amount
→ 检查受影响行数
→ 同事务创建Voucher
→ 失败补偿Redis
→ 定期对账
```

要主动说明：Redis 与 MySQL 之间仍有失败窗口，补偿也可能失败，因此需要重试、告警和对账。

## 八、核销幂等

场景：商户重复点击、客户端超时重发、网关重试、并发请求。

防线：

- 请求幂等键/商户订单号。
- 数据库唯一约束。
- Voucher 状态条件更新。
- 必要时版本号/受影响行数判断。
- 重复请求返回首次成功结果或明确冲突。

锁只是过程手段，状态机和数据库约束才是最终防线。

## 九、数据库设计回答

不要背表名，要讲不变量：

- 同一用户/活动是否只能有一份申请。
- 状态允许哪些迁移。
- Outbox/Inbox 如何唯一。
- Voucher 如何保证一券一销。
- 商户订单号如何去重。
- 额度更新如何防止负数。

每个不变量至少给出“应用校验 + 数据库约束/条件更新”两层证据。

## 十、系统设计追问

### QPS 增长十倍

先量化瓶颈：数据库、Redis 热 Key、MQ 消费、线程/连接池。可选演进：读缓存、批量、索引、异步化、消费者扩展、热点拆分、限流降级。不能直接回答“加机器”。

### RabbitMQ 故障

申请与 Outbox 同事务仍可提交；发送失败保持 PENDING 并重试。需要监控积压、失败次数和最长等待，恢复后受控补发。

### Redis 故障

根据业务选择失败关闭或降级到数据库受控路径；数据库条件更新仍是最终正确性，但必须限流防止数据库被打穿。

### MySQL 主库变慢

上游线程和连接会排队，应快速超时、限流、停止非核心任务、检查慢 SQL/锁/资源，避免 Redis/MQ 重试进一步放大。

## 十一、项目证据等级

| 标签 | 含义 | 面试表达 |
|---|---|---|
| 已实现 | 代码与配置存在 | “项目中实现了……” |

## 十二、5 分钟项目回答结构

```text
30秒：业务和个人职责
60秒：申请到核销主链
90秒：挑一个难点讲问题、方案和证据
60秒：讲失败窗口与兜底

30秒：总结取舍和下一步
```

## 十三、项目必会追问

1. 为什么需要 Outbox，直接事务后发消息不行吗？
2. Confirm、Return、ACK 分别证明什么？
3. Redis 预占成功而数据库失败怎么办？
4. 消费者业务成功但 ACK 前宕机怎么办？
5. 唯一约束冲突如何映射为幂等结果？
6. 如何证明没有超发和一券多销？
7. 系统最大的单点和容量瓶颈是什么？
8. 哪些能力只是设计过而未实现？
