# 并发工具选型

[[01-集合与Map选型|上一篇：集合]] · [[00-Java后端面试知识地图|知识地图]] · [[03-JVM内存-GC与排查|下一篇：JVM]]

## 1. 先判断问题

```text
只需要状态可见/安全发布 → volatile
单变量简单原子更新 → Atomic/CAS
多步骤或多变量必须整体成立 → synchronized/ReentrantLock
数据库并发不变量 → SQL条件更新、锁、事务、唯一约束
```

| 工具 | 保证 | 不保证/代价 |
|---|---|---|
| volatile | 可见性与相关有序性 | `i++` 等复合操作不原子 |
| CAS/Atomic | 单次比较并更新原子 | ABA；高竞争重试耗 CPU |
| synchronized | 同一锁临界区互斥；锁的 happens-before | 锁范围不当降低并发，可能死锁 |
| ReentrantLock | 显式可重入锁，支持 tryLock、可中断、公平策略、Condition | 必须在 finally 解锁 |

## 2. synchronized

判断是否互斥，只看是不是同一把对象锁：实例同步方法锁 `this`，静态同步方法锁 `Class`，同步块锁括号表达式得到的对象。它可重入，正常返回或异常退出都会释放锁。

字节码：同步方法使用 `ACC_SYNCHRONIZED`；同步块使用 `monitorenter/monitorexit` 并配合异常处理路径。

> [!warning] JDK版本边界
> 不要无条件背“无锁→偏向锁→轻量级锁→重量级锁且只升不降”。锁实现属于 HotSpot 版本细节；偏向锁在较新 JDK 中已不再是默认主线。面试先讲 Monitor、互斥、可重入和 happens-before，被追问时再说明具体 JDK 版本。

## 3. volatile 与 CAS

`volatile i++` 仍不安全，因为它是读、计算、写回三步。CAS 的 V/A/B 比较和条件写入是一次原子动作；CAS 失败后是否循环重试是上层策略，CAS 本身不等于自旋。

ABA：值经历 A→B→A，单纯比较值无法感知中间变化，可使用版本戳等方式解决。

## 4. ReentrantLock

```java
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();
}
```

普通临界区优先用更简单的 `synchronized`；确实需要超时、尝试获取、可中断、公平策略或多个 Condition 时再选 ReentrantLock。

## 5. 线程池七个参数的因果链

```text
任务到达
→ 未达到corePoolSize：创建核心线程
→ 核心线程忙：进入workQueue
→ 队列满且未到maximumPoolSize：创建非核心线程
→ 线程和队列都满：执行拒绝策略
```

`keepAliveTime` 主要控制空闲非核心线程存活时间；是否让核心线程超时取决于额外配置。实际参数必须根据任务 CPU/IO 特征、延迟目标、下游容量和压测结果确定，不能机械套公式。

## 6. 60 秒回答

> 并发工具要按问题选。只需要状态可见或安全发布用 volatile，但它不能让 `i++` 原子；单变量简单更新可用 Atomic/CAS，注意 ABA 和高竞争自旋成本；多步骤或多变量必须整体成立时用锁。普通临界区优先 synchronized，需要 tryLock、超时、可中断或多个 Condition 时用 ReentrantLock。线程池则按核心线程、队列、最大线程和拒绝策略形成的任务流来解释，并通过压测和下游容量定参数。
