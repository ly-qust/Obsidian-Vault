
## 一、先建立脑内判断链（最重要）

遇到并发题，**第一步永远不是选工具，而是定性问题**：

```
共享可变数据
  │
  ├─ 只是发布状态 / 传递可见性？      → volatile
  ├─ 简单单值原子更新（计数/状态机）？ → CAS / 原子类
  └─ 多变量 / 多步骤必须整体成立？     → synchronized
```

> 面试大忌：一上来就说"用 synchronized"。先讲清楚你判断的是哪类问题，再选方案。

---

## 二、并发三大问题（定性用）

| 问题      | 一句话本质                  | 经典反例                           |
| ------- | ---------------------- | ------------------------------ |
| **可见性** | 一个线程改了，另一个线程**何时能看到**  | `running=false` 已改，工作线程仍死循环    |
| **原子性** | 一个操作执行期间，**能否被其他线程插入** | 两个线程各 `count++` 一次，结果只 +1      |
| **有序性** | 其他线程观察到的操作**顺序是否符合约束** | 看到 `ready=true`，却看不到 `data=42` |

**`count++` 丢失更新的交错（必须能手画）：**

```
线程A: 读0 → 算1 → 写回1
线程B:      读0 → 算1 → 写回1
结果：执行两次加一，最终是 1
```

## 三、三者核心对比（一张表背完）

|维度|synchronized|volatile|CAS|
|---|---|---|---|
|**核心机制**|对象内置锁/Monitor，互斥进入|volatile 读写的内存语义|比较预期值并条件原子更新|
|**解决什么**|临界区互斥、复合操作一致性|状态可见、发布、相关有序性|单值/简单状态原子更新|
|**可见性**|✅ 解锁→后续加锁建立 happens-before|✅ 写→后续读建立 happens-before|取决于 API，原子类常用 CAS 有|
|**原子性**|✅ 临界区整体互斥|❌ `i++` 仍不原子|✅ "比较+写入"本身原子|
|**有序性**|✅ 锁边界限制重排|✅ 限制 volatile 读写前后相关重排|看具体 API|
|**是否阻塞**|竞争时可能阻塞等待|不阻塞|单次不阻塞；重试循环占 CPU|
|**典型场景**|转账、库存扣减、多字段不变量|停止标志、配置发布、单写多读|原子计数、简单状态机|
|**最大局限**|竞争带来上下文切换；锁范围影响并发|无互斥，不能保护"检查后执行"|ABA、高竞争重试烧 CPU、复杂逻辑难写|
|**面试关键词**|锁对象、互斥、可重入、Monitor、happens-before|可见性、顺序约束、非复合原子|V/A/B、乐观更新、重试、ABA|

> **破除三个常见误解：**
> 
> 1. synchronized ≠ 只管原子性（它也管可见性和有序性）
> 2. volatile ≠ 只管可见性（它也管相关有序性，但不管复合原子性）
> 3. CAS ≠ 一定不阻塞、一定更快（高竞争下重试比锁还慢）

## 四、synchronized 核心考点

### 1. 锁对象是谁（面试必问）

| 写法                             | 锁对象           | 不同实例是否互斥    |
| ------------------------------ | ------------- | ----------- |
| `synchronized void m()`        | `this`        | ❌ 不同实例不互斥   |
| `static synchronized void m()` | `Demo.class`  | ✅ 全类共享一把锁   |
| `synchronized (obj) {}`        | `obj` 求值得到的对象 | 只有同一对象才互斥   |
| `synchronized (Demo.class) {}` | `Demo.class`  | 与静态同步方法同一把锁 |

**判断互斥的唯一标准：锁的是不是同一个对象。**

- 同一实例的两个实例同步方法 → 都锁 `this` → 互斥
- 不同实例的实例同步方法 → 锁不同 → 不互斥
- 静态同步方法 vs 实例同步方法 → 一个锁 Class、一个锁 this → 不互斥

### 2. 可重入（必须会背）

> 同一线程持有某对象的内置锁时，可以再次进入由该对象保护的同步方法/块；JVM 记录重入次数，逐层退出匹配后才真正释放。

**为什么必须可重入？** 同步方法 A 调用同步方法 B，如果不可重入，线程会等自己释放锁 → 自我死锁。

### 3. 字节码层面（你上一张图的考点）

- **同步方法**：打 `ACC_SYNCHRONIZED` 访问标志，方法内**看不到** monitorenter/monitorexit，由 JVM 隐式加解锁
- **同步代码块**：不打标志，显式插入 `monitorenter` + `monitorexit`，还要生成异常处理器保证异常时释放锁

### 4. 一句话定位

> 让线程持有**同一对象的内置锁**后互斥执行临界区，适合保护复合状态；正常返回和异常退出都会释放锁。

## 五、volatile 核心考点

### 1. 两个保证

- **可见性**：对 volatile 字段的写 **happens-before** 后续对同字段的读
- **有序性**：限制 volatile 读写前后的相关重排（不是禁止一切重排）

### 2. 经典发布模型（必须理解）

```
holder.data = 42;        // 普通写
holder.ready = true;     // volatile 写（发布信号）

if (holder.ready) {      // volatile 读
    System.out.println(holder.data);  // 一定能看到 42
}
```

`ready` 不只是布尔值，而是"前面初始化已完成"的**发布信号**。volatile 写之前的普通写不能被重排到发布之后。

### 3. 为什么 `volatile i++` 仍不安全（高频追问）

`i++` = 读 → 算 → 写回，三个步骤。volatile 只保证**单次**读写可见，**不会在三个步骤周围加互斥**。两个线程仍能同时读到同一个旧值并覆盖写回。

> 结论：volatile 不能把"读改写"组合成不可分割的原子操作。计数用 `AtomicInteger` 或 synchronized。

### 4. 适用边界

|适合|不适合|
|---|---|
|独立停止标志|计数自增|
|配置/对象引用安全发布|余额扣减|
|单写多读状态|先检查后执行|
|更新不依赖旧值|多字段必须同时变化|

## 六、CAS 核心考点

### 1. 三要素

- **V**：内存位置当前值
- **A**：预期旧值
- **B**：希望写入的新值

```
CAS(V, A, B): V == A ? 原子写入B并返回成功 : 不修改并返回失败
```

安全的关键：**比较和条件写入是一个不可分割的动作**，不是"比较原子 + 写入原子"分开。

### 2. CAS vs 自旋（别混淆）

- **CAS 本身**：只尝试一次，失败就返回，不等待
- **自旋**：CAS 失败后，业务要求必须完成 → 重新读取、计算、再 CAS → 循环才叫自旋

> 面试表述：CAS 不等于自旋，自旋是 CAS 失败后的重试策略。

### 3. ABA 问题

```
线程1读A → 线程2把A改成B又改回A → 线程1 CAS 发现还是A → 成功
```

本质：CAS 只比较当前值，**看不到中间是否发生过对业务有意义的变化**。 解决：值 + 版本号一起比较（`AtomicStampedReference`）。

### 4. 性能真相

> CAS 不一定比 synchronized 快。低竞争、短操作下 CAS 能避免阻塞；高竞争下反复失败烧 CPU，可能还不如锁。复杂临界区用多个 CAS 还会增加正确性成本。

## 七、面试高频追问 30 秒速答

| 问题                       | 核心答案                                               |
| ------------------------ | -------------------------------------------------- |
| synchronized 保证什么？       | 同一把锁的互斥 + 解锁→加锁的 happens-before（可见性+有序性）           |
| 锁的是什么？                   | **对象**，不是代码。实例方法锁 this，静态方法锁 Class，块锁指定对象          |
| 可重入是什么？                  | 同一线程可重复获取同一锁，计数归零才释放，避免自我死锁                        |
| volatile 怎么保证可见性？        | 写 happens-before 后续读；不要只答"直接读主内存"（过度简化）            |
| volatile 为什么不能保证 i++？    | i++ 是读-算-写三步，volatile 不在三步周围加互斥                    |
| CAS 是什么？                 | V/A/B，只有当前值等于预期值才原子写入新值，否则失败                       |
| CAS 为什么需要自旋？             | CAS 只试一次，业务要求必须完成时才循环重试                            |
| ABA 是什么？                 | A→B→A，只看当前值看不到中间变化，用版本号解决                          |
| CAS 一定比 synchronized 快吗？ | 不一定，高竞争重试烧 CPU，复杂临界区锁更合适                           |
| 三者怎么选？                   | 状态可见用 volatile，简单原子更新用 CAS/原子类，复合不变量用 synchronized |

## 八、闭卷必背口诀

```
synchronized：同一对象锁 + 互斥 + 可重入 + 锁的 happens-before
volatile    ：可见性 + 相关顺序约束，不提供复合操作互斥
CAS         ：V/A/B + 原子比较更新 + 失败可重试
```

**三句保命话：**

1. 判断两个同步方法是否互斥，看它们锁的是不是**同一个对象**。
2. "看见最新值"不能让"读改写"自动变成**不可分割操作**。
3. 正确性优先：简单可见状态用 volatile，简单原子更新用 CAS，复杂临界区用锁。
