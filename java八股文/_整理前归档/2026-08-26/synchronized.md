## 一、是什么

**一句话：** synchronized 是 Java 的内置同步机制，线程进入同步方法/块前必须先取得**指定对象的内置锁**，同一把锁同一时刻只允许一个线程持有，从而让临界区互斥执行。

**通俗类比：** synchronized 像公共厕所的隔间门。一次只能进一个人，进去后锁门，其他人在外面等。出来开门后，下一个人才能进。

> 关键认知：**锁的是对象，不是代码，也不是变量。** 代码块只是"被保护的区域"，真正起互斥作用的是你括号里那个对象的锁。

---

## 二、到底保证什么（别只背"原子性"）

很多人以为 synchronized 只管原子性，错。它同时保证三件事：

| 特性      | 怎么保证的                                              |
| ------- | -------------------------------------------------- |
| **原子性** | 同一把锁的临界区一次只允许一个线程执行，其他线程不能插入                       |
| **可见性** | 解锁 happens-before 后续对同一把锁的加锁 → 后进入的线程能看到前一个线程的所有写入 |
| **有序性** | 锁边界限制临界区相关的重排，另一个线程观察到的顺序符合约束                      |


**面试表述：** synchronized 对使用同一把锁的代码提供互斥，并借助"解锁先行发生于后续加锁"的 happens-before 语义提供可见性与有序性。

> ⚠️ 边界：它只能约束**使用了同一把锁**的访问。如果有代码根本没加锁就去读共享变量，synchronized 管不了它。

## 三、锁对象是谁（最核心考点，面试必问）

### 四种写法对应四个锁对象

|写法|锁对象|不同实例是否互斥|
|---|---|---|
|`synchronized void m()`|当前实例 `this`|❌ 不同实例不互斥|
|`static synchronized void m()`|类的 `Class` 对象（`Demo.class`）|✅ 全类共享一把锁|
|`synchronized (obj) {}`|`obj` 表达式求值得到的对象|只有 `obj` 是同一对象才互斥|
|`synchronized (Demo.class) {}`|`Demo.class`|与该类静态同步方法同一把锁|

### 判断互斥的唯一标准

> **锁的是不是同一个对象。是 → 互斥；不是 → 不互斥。**

### 三个经典判断（必须秒答）

1. **同一实例的两个实例同步方法** → 都锁 `this` → **互斥**
2. **不同实例的实例同步方法** → 锁不同对象 → **不互斥**
3. **静态同步方法 vs 实例同步方法** → 一个锁 `Class`、一个锁 `this` → **不互斥**

### 等价理解

```
// 实例同步方法
synchronized void m() { body; }
// 等价于
void m() {
    synchronized (this) { body; }
}

// 静态同步方法
static synchronized void m() { body; }
// 等价于
static void m() {
    synchronized (Demo.class) { body; }
}
```

### 工程实践：锁对象怎么选

- 语法上任何非 null 引用都能当锁
- 工程上选**生命周期稳定、不会被外部随意替换**的对象
- 推荐写法：`private final Object lock = new Object();`
- ❌ 别用 `synchronized (this)` 在对外暴露的类上（外部也可能锁你的实例，导致意外死锁）
- ❌ 别用字符串常量（`"lock"`）当锁，JVM 字符串常量池可能导致意外共享
- ❌ 别用 `Integer` / `Long` 等包装类（自动装箱可能创建新对象，锁就变了）

synchronized 有两种字节码实现，**面试经常对比考**：

|实现方式|对应写法|字节码表现|
|---|---|---|
|**方法标志**|同步方法（实例/静态）|方法访问标志打 `ACC_SYNCHRONIZED`，方法体内**看不到** monitorenter/monitorexit|
|**显式指令**|同步代码块 `synchronized(obj){}`|不打方法标志，块开头插入 `monitorenter`，结尾插入 `monitorexit`，还要生成异常处理器|

### 为什么同步方法用标志而不是指令？

1. **字节码更干净**：不用每个方法都插 monitorenter/monitorexit
2. **异常释放由 JVM 内部处理**：方法抛异常退出时，JVM 检测到 `ACC_SYNCHRONIZED` 自动释放锁，不需要编译器额外生成异常处理表
3. 同步代码块则必须编译器生成异常处理器，保证异常时执行 monitorexit（否则锁泄漏）

### 实操验证

写一个同步方法，用 Jclasslib 打开 → 访问标志里有 `ACC_SYNCHRONIZED`，字节码列表找不到 monitorenter。 写一个 `synchronized(this){}` 代码块 → 字节码里能看到 monitorenter、monitorexit，还有异常表。

## 五、可重入（必须会背）

### 是什么

> 同一线程持有某对象的内置锁时，可以再次进入由该对象保护的同步方法或同步块；JVM 记录重入次数，逐层退出匹配后才真正释放。

### 代码示例

```
class Service {
    synchronized void methodA() {
        methodB();  // 已经持有 this 锁，还能再进 methodB
    }
    synchronized void methodB() {
        // 两个方法都锁 this
    }
}
```

### 为什么必须可重入

如果不可重入：线程执行 methodA 持有 this 锁 → 调用 methodB 试图再拿 this 锁 → 拿不到，阻塞等待 → 但锁在自己手里，自己又在等 methodB 返回 → **自我死锁**。

### 类比

你进了厕所隔间锁了门，突然想拿隔间外的纸巾，又出不去——可重入就是允许你"已经在里面的人"可以反复开关这扇门，不用每次都重新排队。

## 六、Monitor 监视器（面试够用版）

### 核心概念

- 每个 Java 对象都关联一个监视器（Monitor）语义，都可以作为内置锁
- 线程进入同步区域，要先获得该对象 Monitor 的**所有权**
- 同一时刻只有一个线程拥有 Monitor，但持有者可以重入
- 离开同步区域（正常返回或异常退出）时释放 Monitor
- 同一把锁的释放 happens-before 后续获取 → 后来者能看到之前的写入

### 竞争队列

拿不到锁的线程进入该对象 Monitor 的**等待队列（EntryList）**，锁释放后被唤醒竞争。

### 面试不要下钻的部分

Mark Word 位结构、ObjectMonitor 源码、`wait/notify` 的 WaitSet 细节——这些属于 JVM 实现层，面试主干只记"每个对象可作为内置锁，获取后互斥进入，正常/异常退出都释放"即可。被追问到再说"JVM 可采用不同实现优化锁"。

## 七、锁升级（面试高频，单独整理必须讲）

JDK 1.6 之后，synchronized 不是一上来就是重量级锁。JVM 会根据竞争情况**自动升级**，目的是减少开销。

### 四种状态

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
```

### 逐个讲

|锁状态|触发场景|工作方式|开销|
|---|---|---|---|
|**无锁**|对象刚创建，没被任何线程锁定|Mark Word 记录对象哈希码等|无|
|**偏向锁**|只有一个线程反复访问，无竞争|把线程 ID 记录到 Mark Word，该线程以后进入不用 CAS，直接判断是不是自己|极低，几乎无额外操作|
|**轻量级锁**|有竞争但竞争不激烈、持有时间短|线程在栈帧创建 Lock Record，CAS 尝试把 Mark Word 指向自己的 Lock Record；失败则自旋重试|中等，自旋占 CPU 但不阻塞|
|**重量级锁**|自旋多次失败、竞争激烈、持有时间长|升级为操作系统互斥量（mutex），拿不到锁的线程阻塞挂起（进入内核态）|高，涉及上下文切换|

### 升级方向

- **只能升级，不能降级**（JDK 15 后偏向锁默认禁用，这里按面试主流答）
- 偏向锁遇到其他线程竞争 → 撤销偏向 → 升级轻量级锁
- 轻量级锁 CAS 失败 → 先自旋 → 自旋一定次数还失败 → 升级重量级锁

### 为什么要升级（设计思想）

> 大部分锁实际上没有竞争或竞争很轻。一上来就用操作系统互斥量（重量级锁），每次加解锁都要进内核态、上下文切换，太贵。所以先用低成本方案，实在扛不住了再升级。

### 类比

- **偏向锁**：这厕所基本只有你一个人用，给你配一把专属钥匙，你来了直接进，不用检查
- **轻量级锁**：偶尔有第二个人来，大家在门口礼貌地原地转圈等一下（自旋），不用去前台登记排队
- **重量级锁**：人越来越多，转圈等太浪费时间，干脆去前台拿号排队（操作系统调度），轮到你再叫你

### 面试注意

- 锁升级是 **JVM 实现优化**，不是 Java 语言规范规定的
- 回答时说"JVM 可采用锁升级优化"即可，不要把 Mark Word 位结构背得太细（除非面试官追问）
- JDK 15 后偏向锁默认被废弃，但面试仍按 1.6~1.8 的主流版本答

## 八、异常与锁释放

### 核心规则

> synchronized 块/方法**无论正常返回还是抛出异常退出，都会释放锁**。

### 为什么代码块需要异常处理器

同步代码块在字节码层面，编译器会自动生成一个异常处理器：如果临界区内抛异常，跳转到 monitorexit 释放锁，再把异常抛出去。否则锁会泄漏，其他线程永远进不来。

同步方法则由 JVM 通过 `ACC_SYNCHRONIZED` 标志隐式处理，不需要显式异常表。

### 注意

- `System.exit()` 会直接终止 JVM，锁不会释放（但 JVM 都没了，锁也没意义了）
- 线程被 `stop()`（已废弃）杀死也可能不释放锁，所以不要用

## 九、常见坑（面试踩分点）

|坑|说明|
|---|---|
|**锁不同对象**|两个同步方法一个锁 this、一个锁其他对象，以为互斥其实不互斥|
|**静态 vs 实例混淆**|静态方法锁 Class，实例方法锁 this，二者不互斥|
|**锁字符串常量**|`"lock"` 在常量池可能被其他代码共享，导致意外互斥|
|**锁可变对象**|锁对象引用被重新赋值（如 `lock = new Object()`），后续线程锁的是新对象，老线程还持有老对象的锁 → 不互斥|
|**锁包装类**|`Integer i = 0; synchronized(i){ i++; }` → i++ 自动装箱创建新对象，锁对象变了|
|**在同步块内调用外部方法**|可能导致死锁（A 锁里调 B 的同步方法，B 锁里调 A 的同步方法）|
|**构造器加 synchronized**|语法不允许 `synchronized` 构造器；构造期间新对象只有当前线程能访问，加锁无意义；不要在构造器里把 `this` 发布给其他线程|
|**锁范围过大**|把不相关的操作也放进同步块，降低并发度|
|**锁范围过小**|把"检查+执行"拆成两个同步块，中间可能被其他线程插入 → 仍不安全|

## 十、面试高频问答（30 秒版）

**Q1: synchronized 是什么？** Java 内置同步机制，线程进入同步方法/块前取得指定对象的内置锁，同一把锁同一时刻只允许一个线程持有，从而保护临界区；解锁与后续加锁还建立可见性和顺序关系。

**Q2: synchronized 锁的是什么？** 锁的是对象，不是代码。实例方法锁 this，静态方法锁 Class 对象，同步块锁括号内表达式求值得到的对象。是否互斥取决于用的是不是同一对象的锁。

**Q3: 可重入是什么意思？** 同一线程持有某把锁后，可以再次进入由同一把锁保护的代码。JVM 记录重入次数，匹配退出后才真正释放。这样同步方法互相调用时不会等待自己造成死锁。

**Q4: synchronized 保证什么？** 对使用同一把锁的代码提供互斥（原子性），并借助"解锁 happens-before 后续加锁"提供可见性与有序性。不能约束根本没使用同一把锁的访问。

**Q5: 同步方法和同步代码块的字节码区别？** 同步方法打 `ACC_SYNCHRONIZED` 访问标志，由 JVM 隐式加解锁，方法内看不到 monitorenter；同步代码块显式插入 monitorenter/monitorexit，并生成异常处理器保证异常时释放锁。

**Q6: 锁升级过程？** 无锁 → 偏向锁（单线程无竞争，记录线程 ID）→ 轻量级锁（有竞争但轻，CAS + 自旋）→ 重量级锁（竞争激烈，操作系统互斥量，阻塞挂起）。只能升级不能降级，目的是在低竞争时减少开销。

**Q7: synchronized 和 ReentrantLock 的区别？** （如果被追问）synchronized 是 JVM 内置、自动释放、可重入、非公平；ReentrantLock 是 API 层面、需手动 unlock、可重入、支持公平/非公平、可中断、可超时、可绑定多个 Condition。性能上 JDK 1.6 后 synchronized 经过锁升级优化，两者差距不大。

**Q8: synchronized 会产生死锁吗？** 会。典型场景：线程 A 持有锁 1 等锁 2，线程 B 持有锁 2 等锁 1。避免方式：固定加锁顺序、减小锁范围、使用 tryLock 超时机制（ReentrantLock）。

3. **不止原子性**——synchronized 同时保证原子性、可见性、有序性。
