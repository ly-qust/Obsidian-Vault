
## 七参数

`ThreadPoolExecutor` 构造方法：

```java
new ThreadPoolExecutor(
    corePoolSize,       // ① 核心线程数
    maximumPoolSize,    // ② 最大线程数
    keepAliveTime,      // ③ 非核心线程空闲存活时间
    unit,               // ④ 时间单位
    workQueue,          // ⑤ 任务队列
    threadFactory,      // ⑥ 线程工厂
    handler             // ⑦ 拒绝策略
);
```

## 一、为什么需要线程池

如果每个任务都创建一个线程，会产生：

- 线程创建和销毁成本
- 每个线程的栈内存和操作系统资源开销
- 线程数量失控，可能导致内存不足
- 线程过多造成上下文切换，降低 CPU 有效利用率
- 大量线程同时访问数据库、Redis、第三方服务，压垮下游资源
- 任务提交速度超过处理速度时，系统无法控制堆积

线程池的作用不只是线程复用，还包括：

```
限制并发线程数
复用线程
缓冲突发任务
控制内存和队列容量
限制下游资源压力
过载时执行拒绝或反压
```

面试表达：

> 线程池的核心价值是控制并发资源，而不只是减少线程创建销毁成本。它通过线程数、任务队列和拒绝策略，把系统的处理能力控制在可接受范围内。

## 二、线程池的整体模型

```
提交任务
   │
   ▼
当前线程数 < corePoolSize？
   │是
   ▼
创建核心线程执行任务
   │否
   ▼
尝试加入任务队列
   │成功
   ▼
排队等待
   │失败：队列已满
   ▼
当前线程数 < maximumPoolSize？
   │是
   ▼
创建非核心线程执行任务
   │否
   ▼
执行拒绝策略
```

对应的设计思想：

```
核心线程：处理平时的常态流量
任务队列：吸收短时间突发流量
非核心线程：队列满后的临时扩容
最大线程数：限制扩容上限
拒绝策略：所有资源耗尽后的过载处理
```

注意：

> 核心线程满了以后，不是立刻创建新线程，而是优先进入队列。只有队列也满了，maximumPoolSize 才有机会生效。

## 三、ThreadPoolExecutor 七个参数

### 1. `corePoolSize`

核心线程数，表示线程池的常态处理能力。

```
corePoolSize = 8
```

不表示线程池启动时一定已经创建 8 个线程，也不表示最多只能同时执行 8 个任务。

默认情况下，核心线程通常在有任务提交时按需创建。可以通过 `prestartAllCoreThreads()` 预先启动。

核心线程默认不会因为空闲而销毁，但以下情况可以退出：

- 调用 `shutdown()`
- 设置 `allowCoreThreadTimeOut(true)`
- 核心线程空闲超过 `keepAliveTime`

配置过大：

- 上下文切换增加
- 内存占用增加
- 可能同时压垮数据库等下游资源

配置过小：

- CPU 或 IO 资源利用不足
- 任务排队时间变长
- 延迟增加

任务类型考虑：

- CPU 密集型：线程数通常接近 CPU 核心数
- IO 密集型：可以比 CPU 核心数多，但受连接池、内存、超时和下游服务限制

---

### 2. `maximumPoolSize`

线程池允许创建的最大线程数。

它不是一开始就生效，而是在以下条件同时满足时才会创建非核心线程：

```
核心线程已满
队列已满
当前线程数 < maximumPoolSize
```

例如：

```
corePoolSize = 2
maximumPoolSize = 4
queueCapacity = 3
```

最多只能额外创建：

```
4 - 2 = 2 个非核心线程
```

如果使用无界队列，队列几乎不会满，`maximumPoolSize` 可能基本没有机会生效。

面试重点：

> `maximumPoolSize` 和队列容量是联动的。队列越大，越不容易创建非核心线程；无界队列甚至可能让最大线程数失去实际意义。

---

### 3. `keepAliveTime`

非核心线程空闲后的存活时间。

例如：

```
keepAliveTime = 60
unit = TimeUnit.SECONDS
```

表示非核心线程空闲 60 秒后可以被回收。

它解决的是流量高峰后的资源释放：

```
高峰期：线程数扩展到 16
高峰结束：非核心线程逐渐空闲
超过 60 秒：非核心线程被回收
恢复到常态线程规模
```

设置太短：

- 线程频繁创建和销毁
- 产生抖动
- 突发流量到来时又要重新创建线程

设置太长：

- 高峰后线程长期占用内存
- 资源释放不及时

默认情况下只影响非核心线程。设置 `allowCoreThreadTimeOut(true)` 后也可以影响核心线程。

---

### 4. `TimeUnit`

`keepAliveTime` 的时间单位，例如：

```
TimeUnit.SECONDS
TimeUnit.MILLISECONDS
TimeUnit.MINUTES
```

它本身不影响任务流转，只负责解释存活时间的单位。

---

### 5. `workQueue`

任务队列，用于暂时保存无法立即执行的任务。

队列解决的是：

> 任务到达速度暂时超过线程处理速度时，提供一个缓冲区。

但队列不是越大越好。

如果：

```
提交速度 = 10000/s
处理速度 = 1000/s
```

那么每秒积压约 9000 个任务：

```
任务堆积
  ↓
内存持续增长
  ↓
任务等待时间越来越长
  ↓
延迟升高
  ↓
最终可能 OOM
```

#### 有界队列

例如：

```
new ArrayBlockingQueue<>(100)
```

优点：

- 控制内存
- 限制任务堆积
- 尽早暴露过载
- 配合拒绝策略形成保护

缺点：

- 容量过小可能频繁拒绝
- 容量过大可能造成较高延迟

#### 无界队列

例如某些 `LinkedBlockingQueue` 的使用方式。

风险：

- 任务无限堆积
- 内存持续增长
- 延迟不可控
- `maximumPoolSize` 可能失去意义
- 过载被隐藏，直到 OOM

#### `ArrayBlockingQueue`

- 有界
- 数组实现
- 容量明确
- 适合需要严格控制堆积量的场景

#### `LinkedBlockingQueue`

- 可以有界，也可以近似无界
- 如果不指定容量，容易产生任务无限堆积风险

#### `SynchronousQueue`

- 不存储任务
- 每个任务必须直接交给工作线程
- 更容易触发创建线程
- 常用于强调直接移交的场景

---

### 6. `ThreadFactory`

线程工厂，负责创建线程。

生产环境常见用途：

- 统一设置线程名称
- 便于日志和监控排查
- 设置守护线程属性
- 设置线程优先级
- 设置未捕获异常处理器

示例：

```
runnable -> {
    Thread thread = new Thread(runnable);
    thread.setName("order-worker-" + thread.getId());
    return thread;
}
```

面试表达：

> ThreadFactory 不只是负责创建线程，更重要的是统一线程的工程属性，尤其是线程命名和异常处理，方便生产问题定位。

---

### 7. `RejectedExecutionHandler`

当线程池已经没有能力接收任务时，决定如何处理新任务。

触发条件：

```
队列已满
且线程数达到 maximumPoolSize
```

---

## 四、四种拒绝策略

### 1. `AbortPolicy`

直接抛出 `RejectedExecutionException`。

特点：

- 默认策略
- 明确暴露系统过载
- 不会静默丢任务

适合：

- 不能无声丢失任务
- 调用方能够捕获异常并处理

处理方式：

```
try {
    executor.execute(task);
} catch (RejectedExecutionException e) {
    // 记录日志和监控
    // 转入 MQ 或补偿队列
    // 或向上游返回可重试错误
}
```

只捕获异常但不补偿，仍然可能造成业务任务丢失。

---

### 2. `CallerRunsPolicy`

由提交任务的线程自己执行任务。

```
线程池满
  ↓
Web 请求线程执行任务
  ↓
请求变慢
  ↓
任务提交速度下降
```

它具有反压效果，因为生产者线程被占用，不能继续高速提交任务。

适合：

- 任务不能轻易丢失
- 可以接受提交线程变慢
- 任务执行时间较短

风险：

- Web 请求线程可能长时间阻塞
- 可能导致接口超时
- 不能解决进程宕机后的任务持久化问题

---

### 3. `DiscardPolicy`

直接丢弃新提交的任务，不抛异常。

适合：

- 允许少量丢失
- 监控指标、非关键日志、过期刷新任务

不适合：

- 订单
- 扣库存
- 支付
- 数据同步
- 任何不能丢失的业务任务

最大风险是：**任务无声丢失，业务方可能完全不知道。**

---

### 4. `DiscardOldestPolicy`

丢弃队列中最老的任务，然后尝试提交当前新任务。

适合：

- 旧数据价值低
- 最新状态比历史任务更重要
- 允许丢弃过期任务

不适合：

- 任务必须按顺序执行
- 每个任务都重要
- 不能丢失历史操作的业务场景

---

## 五、任务流转示例

配置：

```
ThreadPoolExecutor(
    2,
    4,
    60,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(3),
    threadFactory,
    handler
);
```

假设之前的任务都没有执行完成，依次提交：

```
T1 → Worker-1，创建核心线程
T2 → Worker-2，创建核心线程

T3 → 进入队列
T4 → 进入队列
T5 → 进入队列

此时：
线程数 = 2
队列 = 3/3

T6 → 队列满，创建 Worker-3
T7 → 队列满，创建 Worker-4

此时：
线程数 = 4
队列 = 3/3

T8 → 队列满且达到 maximumPoolSize
     → 执行拒绝策略

T9、T10 → 同样触发拒绝策略
```

关键理解：

> T6 不直接创建线程，是因为线程池优先利用队列吸收突发流量。只有队列容量也耗尽，才进行昂贵的线程扩容。

## 六、完整配置分析

```
ThreadPoolExecutor executor = new ThreadPoolExecutor(
        8,
        16,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(100),
        threadFactory,
        new ThreadPoolExecutor.CallerRunsPolicy()
);
```

面试分析：

1. 常态核心线程数是 8。
2. 最大线程数是 16。
3. 8 个核心线程都忙时，新任务先进入队列。
4. 队列最多保存 100 个等待任务。
5. 队列满后，才创建第 9 到第 16 个非核心线程。
6. 队列满且线程数达到 16 时触发拒绝策略。
7. 非核心线程空闲 60 秒后回收。
8. 如果提交速度长期大于处理速度，队列会持续堆积。
9. 使用 `CallerRunsPolicy` 后，提交线程会自行执行任务，从而降低提交速度。
10. 如果任务执行时间很长，线程会长期被占用，队列更容易堆积，最终可能触发反压、拒绝或请求超时。

## 七、线程池常见生产问题

### 1. 队列堆积

原因：

- 任务执行慢
- 提交速度过快
- 线程数过少
- 下游 IO 阻塞
- 数据库连接不足

排查：

- 活跃线程数
- 当前线程数
- 队列大小
- 完成任务数
- 任务平均耗时和最大耗时
- 拒绝次数
- CPU、内存、GC
- 数据库连接池和接口超时

处理：

- 优化任务耗时
- 设置合理超时
- 拆分慢任务
- 调整线程数和队列容量
- 做任务隔离
- 增加限流或降级
- 必要时引入 MQ

### 2. OOM

典型原因：

```
无界队列
  ↓
任务持续堆积
  ↓
内存持续增长
  ↓
最终 OOM
```

### 3. 线程数过多

可能导致：

- 上下文切换增加
- 内存占用增加
- CPU 使用率升高
- 数据库连接耗尽
- 下游服务被打垮

### 4. 任务执行很慢

可能导致：

- 工作线程长期占用
- 队列持续增长
- 非核心线程全部创建
- 最终触发拒绝策略

## 八、线程池和 MQ 的区别

|对比项|线程池|MQ|
|---|---|---|
|作用范围|进程内|通常跨进程、跨服务|
|存储位置|内存|通常支持持久化|
|服务重启|任务可能丢失|消息通常可以保留|
|削峰能力|有限|更强|
|重试机制|需要自己实现|通常有配套能力|
|可靠投递|较弱|更适合|
|典型用途|并发执行任务|异步解耦、削峰、可靠传递|

核心结论：

> 线程池解决进程内的并发执行和资源控制；MQ 解决跨服务异步解耦、削峰和可靠投递。实际系统中经常是 MQ 负责保存任务，消费者内部再使用线程池并发处理。

## 九、面试高频问题和简答

### 1. 为什么需要线程池？

> 线程池可以复用线程，减少创建销毁成本，更重要的是限制并发数量、缓冲突发任务、保护 CPU、内存和下游资源，并在系统过载时执行拒绝或反压。

### 2. `corePoolSize` 和 `maximumPoolSize` 的区别？

> `corePoolSize` 是常态线程数，`maximumPoolSize` 是队列满后允许扩展到的最大线程数。

### 3. 核心线程满了后为什么先入队？

> 因为队列可以吸收短时突发流量，避免每次核心线程忙时都创建新线程，降低线程创建和调度成本。

### 4. `maximumPoolSize` 什么时候生效？

> 核心线程满了、任务队列也满了，并且当前线程数还没达到最大线程数时，才会创建非核心线程。

### 5. 无界队列有什么风险？

> 任务可能无限堆积，导致延迟越来越高、内存持续增长并最终 OOM，同时最大线程数几乎失去扩容意义。

### 6. `CallerRunsPolicy` 为什么能反压？

> 因为提交任务的线程被迫执行任务，不能继续高速提交，从而降低生产速度。

### 7. 为什么不建议直接使用 `Executors`？

> 某些工厂方法会使用无界队列或可能创建大量线程，容易导致任务堆积、内存问题或线程失控。生产环境通常显式创建 `ThreadPoolExecutor`，明确设置参数。

### 8. CPU 密集型和 IO 密集型怎么设置？

> CPU 密集型线程数接近 CPU 核心数；IO 密集型可以更多，但必须结合 IO 等待比例、连接池、超时、内存和下游承载能力综合确定。

### 9. 订单任务适合什么拒绝策略？

> 订单任务不能静默丢失，不能只依赖内存线程池，通常使用 MQ 或持久化任务机制，配合重试、幂等和死信处理。

### 10. 线程池是不是线程越多越好？

> 不是。线程数过多会增加内存占用和上下文切换，还可能压垮数据库、连接池和下游服务。

## 十、最后的四层记忆模型

### 第一层：一句话

> 线程池就是用有限数量的线程，有序处理大量任务，并在过载时控制系统行为。

### 第二层：完整原理

```
核心线程
  ↓
任务队列
  ↓
非核心线程
  ↓
拒绝策略
```

### 第三层：生产实践

- 通常优先使用有界队列
- 根据任务类型设置线程数
- 给线程命名
- 监控队列长度、活跃线程数和拒绝次数
- 设置任务超时
- 关键任务不要只放内存队列
- 过载时要有降级、重试或 MQ 方案
- 不同业务使用不同线程池，避免互相影响

### 第四层：自然面试表达

> 我理解线程池不是简单地把线程复用起来，而是对并发资源进行控制。任务进来后，先使用核心线程；核心线程满了先进入队列，队列满了才创建非核心线程，达到最大线程数后再执行拒绝策略。这样可以吸收短时突发流量，同时限制线程和内存资源。生产环境要重点关注队列是否有界、任务是否会长期阻塞、拒绝策略是否会丢数据，以及数据库和第三方服务是否能承受实际并发。对于订单这类关键任务，线程池只能负责进程内执行，可靠保存和重试通常要交给 MQ 或持久化任务机制。
