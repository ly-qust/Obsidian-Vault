# 一、并发来源：为什么这个系统会高并发

这种补贴类系统的并发不是持续均匀的，而是**短时间流量爆发型并发（Burst Traffic）**。

现实中的典型场景：

- 政府宣布补贴政策
    
- 活动开始时间（例如 10:00）
    
- 名额有限
    
- 用户同时申请
    

例如：

```
10万用户
↓
5分钟内
↓
同时申请补贴
```

这就是典型的**突发型高并发业务**。

所以系统会出现：

- 同时大量查询资格
    
- 同时提交申请
    
- 同时抢占补贴额度

# 二、并发压力点在哪里

这个项目至少有 **4 个高并发场景**。

---

# 1 资格预检并发

用户首先会查询：

```
我有没有资格申请补贴？
```

例如输入：

- 身份证
    
- 城市
    
- 商品类型
    
- 是否旧机回收
    

系统会立即返回：

```
✔ 可以申请
✔ 可申请金额
✔ 需要补充材料
```

### 并发特点

假设：

```
2000人同时点击
“资格检测”
```

系统需要：

- 查询补贴规则
    
- 判断条件
    
- 返回结果
    

如果没有缓存：

数据库会被打爆。

### 解决方式

Redis缓存：

```
补贴规则
活动信息
资格规则
```

这样：

```
查询 → Redis
而不是 → MySQL
```

并发能力会从：

```
100QPS
→
5000QPS
```

---

# 2 申请提交并发

通过预检之后，用户会提交正式申请：

```
提交申请
上传材料
提交订单
```

这个操作会触发很多逻辑：

```
写入申请表
写入材料表
发送审核任务
```

如果没有削峰：

```
1000用户同时提交
↓
数据库写入1000次
↓
数据库压力巨大
```

### 解决方式

RabbitMQ削峰：

```
用户提交
↓
写入申请表
↓
发送 MQ
↓
后台异步审核
```

这样：

```
用户请求 2000TPS
↓
MQ队列排队
↓
后台慢慢处理
```

这就是典型：

**削峰填谷架构**

---

# 3 额度池竞争并发（核心并发）

这是这个系统**最关键的并发点**。

假设：

```
补贴额度：1000万
单人补贴：1000
可发放人数：10000
```

但是：

```
20000人同时申请
```

系统必须保证：

```
✔ 不超发
✔ 不重复发
✔ 不出现负数额度
```

如果处理不好会出现：

```
额度 -20000
```

这是典型：

**共享资源竞争并发问题**

---

### 解决方式

先 Redis 预扣减：

```
Redis quota = 10000
```

用户申请：

```
Redis quota --
```

再 DB 乐观锁：

```
update quota
set remain = remain - 1
where id = 1
and version = ?
```

如果冲突：

```
重试
```

这就是经典：

**库存/额度竞争模型**

---

# 4 商户核销并发

用户拿到补贴券之后：

去商户消费。

商户会核销：

```
扫码券码
```

并发问题：

```
同一张券
被重复核销
```

或者：

```
100商户同时核销
```

系统必须保证：

```
券只能用一次
```

解决方式：

```
乐观锁
状态校验
Redis锁
```

# 三、系统内部并发（你可以在答辩讲）

除了用户并发，还有**系统内部并发**。

例如：


后台会同时执行：

```
OCR识别
规则校验
AI分析
风控检测
通知发送
```

也就是说：

```
1个请求
→
拆成5个任务
```

这叫：

**任务级并发**

# 四、Java21虚拟线程并发

这个项目还可以体现一个非常新的技术：

**Java21虚拟线程**

传统线程：

```
1线程 = 1任务
```

虚拟线程：

```
1万任务
只需要几十个内核线程
```

适合：

```
IO密集任务
```

例如：

```
AI调用
材料校验
规则查询
商户验证
```

虚拟线程可以大幅提高并发处理能力。
