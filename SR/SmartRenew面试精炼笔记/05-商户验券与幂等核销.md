# 商户验券与幂等核销

[[04-额度预占与可靠发券|上一篇：额度与发券]] · [[00-SmartRenew项目知识地图|知识地图]] · [[06-数据库约束与并发防线|下一篇：数据库防线]]

## 1. 先分清验券与核销

```text
验券 verify：只判断是否可用，不修改为USED。
核销 redeem：把ISSUED原子更新为USED，并写write_off记录。
```

验券检查：商户合法且品类匹配、券存在、未作废、未过期、未核销、状态为 ISSUED。

## 2. Controller 请求边界

```text
POST /api/v1/merchant/vouchers/{voucherCode}/redeem
Header: Idempotency-Key
Body: orderNo、remark
```

Controller 完成参数校验和当前商户身份解析，再交给 Service。`orderNo` 使用 `@NotBlank`；商户身份由当前登录用户与 `merchant_user_rel` 关联确定。

## 3. 四道防线

| 防线 | 解决什么 | 关键点 |
|---|---|---|
| 幂等键 | 同一请求因超时、重试被重复发送 | 同一商户同一 key 直接返回首次结果 |
| 商户订单号 | 同一商户业务订单重复提交 | 唯一 `(merchant_id, order_no)` |
| 条件更新 | 两个请求同时核销同一张券 | `id + status=ISSUED + version`，只有一个更新成功 |
| 券唯一约束 | 任何路径都不能一券多条核销记录 | `UNIQUE(voucher_id)` 最终兜底 |

> [!important] 作用域
> 设计允许不同商户使用相同的订单号或幂等键，因此唯一键带 `merchant_id`。它阻止的是“同一商户内重复”，不是阻止不同商户出现相同字符串。`voucher_id` 唯一才保证一张券全局只能核销一次。

## 4. 为什么“先查再更新”不安全

```text
A查到ISSUED ─┐
             ├→ 两边都认为可核销
B查到ISSUED ─┘
```

正确做法把判断写进 UPDATE：

```sql
UPDATE voucher
SET status = 'USED',
    write_off_time = ?,
    version = version + 1
WHERE id = ?
  AND status = 'ISSUED'
  AND version = ?;
```

必须检查受影响行数：`1` 表示获胜；`0` 表示状态或版本已变化。

## 5. 两个并发请求在 InnoDB 中发生什么

```text
A、B都读到ISSUED/version=0
→ A先执行UPDATE并持有记录锁
→ B的UPDATE等待A
→ A提交后，B重新判断WHERE
→ status/version已变化，B影响0行
```

若 A 回滚，旧状态恢复，B 等待结束后可能满足条件并更新成功。业务上仍只有一个最终成功者。

## 6. 事务到底保证什么

`@Transactional` 保证“Voucher 变为 USED”和“插入 write_off”一起提交或一起回滚。如果插入核销记录失败且异常导致事务回滚，券会恢复为 ISSUED。事务本身不负责决定两个并发请求谁成功；并发胜者由条件更新和唯一约束决定。

## 8. 90 秒回答

> 核销需要同时解决重试幂等和并发一券多销。请求先携带 `Idempotency-Key` 和商户订单号；同一商户同一幂等键会返回首次结果，同一商户订单号由联合唯一索引防止复用。通过业务校验后，Voucher 使用 `id + ISSUED状态 + version` 做条件更新并检查受影响行数，两个并发请求即使都读到旧状态，也只有一个能把券改成 USED。随后在同一事务内写入 `write_off`，`UNIQUE(voucher_id)` 再做最终兜底。任何异常导致事务回滚时，券状态和核销记录一起回滚。
