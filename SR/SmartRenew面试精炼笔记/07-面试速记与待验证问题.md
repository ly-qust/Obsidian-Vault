## 高频速答

### 1. JWT 校验通过后，权限放在哪里？

创建包含 principal 和 authorities 的 `Authentication`，再写入 `SecurityContext`。URL 角色规则读取 authorities；业务数据权限由 Service 再按当前用户或商户校验。

### 2. 401 与 403 有什么区别？

401 是未建立有效身份；403 是身份有效但权限不足。跨用户访问还可能由业务层按统一策略返回 403 或资源不存在。

### 3. Outbox 解决了什么？

把业务修改和待发送事件放在同一本地事务中，避免数据库与 MQ 双写失配；发送仍需要提交后触发、失败重试和监控。

### 4. 为什么既有 Redis 预占又有 MySQL 条件扣减？

Redis 负责高吞吐和快速失败，MySQL 是权威事实源；条件更新、事务和唯一约束负责最终防超发，失败时补偿 Redis。

### 5. 幂等键、订单号和券唯一键有什么区别？

幂等键标识同一商户请求重试；订单号标识商户业务单；`voucher_id` 唯一保证一张券全局只能有一条核销记录。

### 6. `@Transactional` 能防止重复核销吗？

不能单独防止。它保证券状态和核销记录一起提交/回滚；并发防重依靠条件更新、受影响行数和唯一约束。

### 7. 两个请求都读到 ISSUED 怎么办？

读到旧状态不代表都能更新。UPDATE 同时要求 `status=ISSUED AND version=?`，InnoDB 串行处理冲突更新；胜者提交后，另一个请求条件不再成立，影响 0 行。

## 今天已理解但尚未实测

- 四类 Security 请求：401、403、参数非法、跨用户访问；
- 真实多线程 + MySQL 的同券并发核销；
- 同幂等键但不同券/订单号的并发冲突行为；
- Redis 预占成功而数据库失败后的补偿故障窗口。

## 仍需弄懂的 3 个问题

1. 当前核销代码在捕获唯一键异常后返回已有结果，事务最终提交还是回滚？是否可能出现“券已改 USED，但本请求核销记录未插入”的边界？
2. 同一个 `Idempotency-Key` 携带不同 `voucherCode` 或 `orderNo` 时，接口应返回首次结果、409 冲突，还是校验请求指纹？
3. Redis 补偿本身失败时，项目用什么任务、幂等记录和对账指标保证最终修复？

这三题是下一轮代码实验的重点，不能用猜测包装成已实现能力。
