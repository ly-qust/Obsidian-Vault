# 数据库约束与并发防线

[[05-商户验券与幂等核销|上一篇：商户核销]] · [[00-SmartRenew项目知识地图|知识地图]] · [[07-面试速记与待验证问题|下一篇：速记]]

## 1. 核心表关系

```text
campaign
├── rule_version
├── quota_pool
└── application ─ material
        ├── outbox → MQ → inbox → review_task → review_log
        └── voucher → write_off ← merchant
```

## 2. 关键唯一约束

| 约束 | 业务不变量 |
|---|---|
| `application(campaign_id, user_id)` | 一个用户对一个活动只能有一份申请 |
| `review_task(application_id)` | 一份申请只创建一个审核任务 |
| `voucher(application_id)` | 一份申请只发一张券 |
| `write_off(voucher_id)` | 一张券只产生一条核销记录 |
| `write_off(merchant_id, order_no)` | 同一商户订单号不能复用 |
| `write_off(merchant_id, idempotency_key)` | 同一商户请求幂等 |
| `mq_inbox(message_key)` | 同一消息只处理一次 |

业务层的“先查询不存在”只能改善提示，不能替代唯一约束，因为并发请求可能同时通过前置查询。

## 3. 四类一致性工具

| 工具 | 解决的问题 |
|---|---|
| 事务 | 多条数据库修改一起提交或回滚 |
| 行锁 / `FOR UPDATE` | 阻止并发事务同时基于旧状态决策 |
| 条件更新 / 乐观锁 | 让状态和版本匹配者才能更新 |
| 唯一约束 | 把业务不变量落实到数据库最终防线 |

## 4. 状态机

不要允许任意状态覆盖，更新必须表达合法迁移：

```text
application: DRAFT → SUBMITTED → APPROVED/REJECTED
voucher: ISSUED → USED/EXPIRED/INVALID
outbox: PENDING → SENT，失败后可重试
inbox: RECEIVED/PROCESSING → CONSUMED/FAILED
```

## 5. 面试回答

> 项目不会只依赖 Java 的 if 校验。事务保证多表修改原子性，`FOR UPDATE` 或条件更新解决并发竞态，状态机限制合法迁移，唯一约束把“一申请一券、一券一核销、同商户请求幂等”等业务不变量落实到数据库。应用层检查负责友好错误，数据库约束负责最终正确性。
