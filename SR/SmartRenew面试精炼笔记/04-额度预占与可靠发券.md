# 额度预占与可靠发券

[[03-申请提交与Outbox-Inbox|上一篇：申请与消息]] · [[00-SmartRenew项目知识地图|知识地图]] · [[05-商户验券与幂等核销|下一篇：商户核销]]

## 1. 为什么 Redis 和 MySQL 都要扣减

| 层次 | 作用 |
|---|---|
| Redis 预占 | 扛住热点流量，快速拒绝额度不足请求 |
| MySQL 条件更新 | 权威事实源，依靠条件和受影响行数防止超发 |
| 事务 | 保证额度扣减、额度日志、Voucher 创建一起成功或回滚 |
| 补偿 | MySQL 或发券失败时归还 Redis 预占额度 |

Redis 提高吞吐，但缓存可能丢失、延迟或与数据库短暂不一致，不能作为唯一正确性防线。

## 2. 核心链路

```text
审核通过
→ Redis原子预占额度
→ MySQL UPDATE ... WHERE available_amount >= amount AND version = ?
→ 检查affectedRows
→ 同事务写额度日志并创建Voucher
→ 成功提交
```

失败路径：

```text
Redis成功，但MySQL条件更新/写日志/发券失败
→ 数据库事务回滚
→ 执行Redis补偿
```

## 3. 为什么还需要唯一约束

- `voucher.application_id` 唯一：同一申请只能生成一张券；
- 额度日志业务键唯一：同一业务操作不能重复记账；
- 条件更新保证余额不会扣成负数；
- 唯一约束处理应用层先查后写的竞态。

## 4. 补偿边界

同步补偿也可能失败，因此成熟方案还需补偿任务、对账、告警和幂等补偿记录。面试不要把“catch 后加回 Redis”说成绝对可靠。

## 5. 60 秒回答

> Redis 预占的目标是吸收热点并快速失败，MySQL 才是额度事实源。预占成功后，MySQL 使用余额条件和版本号做原子更新，并检查受影响行数；额度扣减、日志和 Voucher 创建放在同一事务中。数据库处理失败时回滚事务并补偿 Redis。Voucher 和额度日志还使用业务唯一约束防重，因此性能由 Redis 提升，最终正确性由 MySQL 条件更新、事务和唯一约束兜底。
