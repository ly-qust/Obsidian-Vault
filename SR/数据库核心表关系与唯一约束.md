
## 一、项目主链路

```text
用户创建并提交申请
        ↓
application：保存申请事实与状态
        ↓ 同一本地事务
mq_outbox：保存待发送的 APPLICATION_SUBMITTED 事件
        ↓ 事务提交后发送；失败定时补发
RabbitMQ
        ↓
消费者检查 mq_inbox
        ↓
审核流水线推进 application / review_task
        ↓
quota_pool：额度预占或扣减
        ↓
voucher：发放补贴券
        ↓
write_off：商户核销
```

核心表职责：

| 表 | 核心职责 | 重要状态/字段 |
|---|---|---|
| `application` | 申请事实与流程状态 | `status`、`campaign_id`、`user_id`、`rule_version_id` |
| `mq_outbox` | 保存待发送事件及重试状态 | `status`、`retry_count`、`next_retry_time`、`event_key` |
| `mq_inbox` | 记录消息消费结果并辅助去重 | `message_key`、`consumer_group`、`status` |
| `quota_pool` | 保存总额度、可用、冻结和已使用额度 | `available_amount`、`frozen_amount`、`used_amount`、`version` |
| `voucher` | 保存发券事实和券状态 | `application_id`、`voucher_code`、`status`、`version` |
| `write_off` | 保存最终核销事实 | `voucher_id`、`merchant_id`、`order_no`、`idempotency_key` |

## 二、申请提交与 Outbox

申请提交审核时，项目在一个 `@Transactional` 方法中：

```text
锁定并检查 application
→ application.status 改为 SUBMITTED
→ 插入 mq_outbox，状态为 PENDING
→ 提交 MySQL 事务
```

这解决了数据库更新与 MQ 发送不能天然原子的问题：

```text
application 与 mq_outbox
要么一起提交，要么一起回滚
```

事务提交后由应用程序发送 RabbitMQ；失败时 Outbox 保留记录，定时任务扫描 `PENDING` 或租约过期的 `SENDING` 记录补发。

必须准确表达：

> Outbox 不是让数据库直接发送消息，也不保证消息只发送一次；它保证业务提交后待发送事件不会因一次发送失败而永久丢失，系统具有补偿依据。

代码证据：

- `ApplicationServiceImpl.submitForReview()`：更新申请并记录事件。
- `ApplicationSubmittedEventPublisher.recordSubmittedEvent()`：写 Outbox，并注册 `afterCommit` 发送。
- `retryPendingOutbox()`：定时扫描补发。
- `MqOutboxServiceImpl`：通过状态和租约条件抢占、标记成功或安排重试。

## 三、Inbox 与重复消费

RabbitMQ 可靠消费通常需要面对“至少一次”语义：

```text
消费者完成业务
→ ACK 前宕机
→ RabbitMQ 重投
```

项目消费者先根据 `message_key` 查询 Inbox：

```text
已处理 → 跳过业务并 ACK
未处理 → 执行业务 → 记录 Inbox → ACK
```

Inbox 主要解决重复投递带来的重复消费问题。

### 当前实现边界

当前代码中，审核业务处理和 `mq_inbox` 成功记录不是同一个本地事务：

```text
业务事务提交成功
→ 写 Inbox 之前宕机
→ 消息重投
→ Inbox 查不到
→ 业务可能再次进入
```

项目依靠业务状态检查、唯一约束和条件更新抵抗一部分重复，但不能把它描述成“仅凭 Inbox 就绝对不会重复”。

更严格的设计是：

```text
开启本地事务
→ 利用唯一约束先插入 Inbox 占位
→ 冲突则不执行业务
→ 插入成功后执行业务
→ Inbox 标记 SUCCESS
→ 业务与 Inbox 一起提交
→ ACK
```

## 四、三个关键唯一约束

### 1. 同活动防重复申请

```sql
UNIQUE (campaign_id, user_id)
```

业务规则：同一个用户在同一个活动中最多创建一份申请，不同用户可以参加同一活动。

并发场景：

```text
请求 A 查询：不存在
请求 B 查询：不存在
A 插入成功
B 插入触发唯一键冲突
```

预查询用于友好提示和减少无效写入；唯一约束才是在写入阶段生效的最终防线。项目捕获数据完整性异常并返回“请勿重复创建”。

### 2. 同申请防重复发券

```sql
UNIQUE (application_id) ON voucher
```

业务规则：一份申请最多对应一张补贴券。即使审核消息重复消费或发券流程重试，也不能为同一申请生成多张券。

### 3. 同一张券防重复核销

```sql
UNIQUE (voucher_id) ON write_off
```

业务规则：一张券最多产生一条核销事实。即使两个商户或两个窗口并发核销同一张券，数据库最终不能落下两条核销记录。

## 五、核销的多层幂等防线

项目 `write_off` 还有两组重要唯一约束：

```sql
UNIQUE (merchant_id, order_no)
UNIQUE (merchant_id, idempotency_key)
```

| 约束 | 防止的问题 |
|---|---|
| `voucher_id` | 同一张券被核销多次 |
| `merchant_id, order_no` | 同一商户订单重复产生核销记录 |
| `merchant_id, idempotency_key` | 同一次接口调用因网络超时重试而重复执行 |

三者不是重复设计，因为防守维度不同：

```text
换幂等键再次核销同一张券 → voucher_id 拦截
换幂等键、换券但重复使用同一商户订单 → merchant_id + order_no 拦截
同一次请求因超时携带相同 Key 重试 → merchant_id + idempotency_key 命中原结果
```

### 两个商户并发核销同一张券

两边的订单号和幂等键都不同，前两组联合唯一约束不会冲突。项目依靠：

```text
第一道：voucher 状态 + version 条件更新
第二道：write_off.voucher_id 唯一约束兜底
```

乐观锁更新可抽象为：

```sql
UPDATE voucher
SET status = 'USED', version = version + 1
WHERE id = ?
  AND status = 'ISSUED'
  AND version = ?;
```

只有一个请求能更新成功；如果极端情况下继续插入核销记录，`UNIQUE(voucher_id)` 仍阻止重复事实。

## 六、为什么不能只依赖 Redis 去重

Redis 适合做快速拦截、短期幂等标记和减轻数据库压力，但不适合作为关键业务唯一防线：

- 去重键可能过期或被淘汰。
- Redis 故障、主从切换或数据丢失可能使标记不存在。
- “先查 Redis 再处理”同样存在并发窗口。
- 缓存状态可能与数据库事实不一致。
- 关键事实最终仍落在 MySQL，应由数据库约束守住业务不变量。

面试结论：

> Redis 是性能防线，数据库唯一约束是正确性防线。关键业务通常采用 Redis 快速拦截、数据库唯一约束或条件更新最终兜底。

## 七、Outbox 与 Inbox 的区别

| 模式 | 所在端 | 主要问题 | 核心做法 |
|---|---|---|---|
| Outbox | 生产者 | 数据库提交成功但消息发送失败 | 业务数据与待发送事件同事务落库，提交后发送并定时补偿 |
| Inbox | 消费者 | 消息重复投递导致重复处理 | 记录消费事实，通过消息唯一键、事务和业务幂等避免重复执行 |

一句话：

> Outbox 防止该发的消息永久丢失，Inbox 防止重复消息造成重复业务。

## 八、表关系答辩表达

> SmartRenew 的主链路从 application 开始，它保存申请事实和状态。申请提交审核时，系统在同一个 MySQL 事务中更新 application 并写入 mq_outbox，事务提交后发送 RabbitMQ，失败则由定时任务补发。消费者通过 mq_inbox 和业务幂等防止重复处理，审核通过后进入额度处理，quota_pool 保存额度状态，voucher 保存发券事实，并通过 application_id 唯一约束防止重复发券。商户核销时写入 write_off，项目同时使用幂等键、商户订单号、券状态乐观锁以及 voucher_id 唯一约束，保证重复请求和并发核销不会生成重复业务事实。

## 九、90 秒项目口述

> SmartRenew 的核心链路是申请、审核消息、额度、发券和核销。用户提交申请时，application 状态更新与 mq_outbox 事件在同一个本地事务中写入，解决数据库提交成功但 MQ 发送失败的问题；事务提交后应用立即发送，失败由定时任务扫描 Outbox 补偿。因为可靠发送可能造成重复投递，消费者使用 mq_inbox、业务状态判断和数据库唯一约束实现幂等。审核通过后处理 quota_pool 并生成 voucher，voucher 上的 application_id 唯一约束保证同一申请不会重复发券。核销阶段使用 merchant_id 加 idempotency_key 处理接口重试，merchant_id 加 order_no 防止商户订单重复，voucher 状态加 version 的条件更新解决并发竞争，最后由 write_off 的 voucher_id 唯一约束兜底。Redis 可以用于快速去重和减压，但不能代替数据库唯一约束，因为缓存可能过期、丢失或与数据库不一致。

## 十、必须诚实说明的实现边界

- 已实现：申请与 Outbox 同事务落库、提交后发送、定时补发、发送确认、重试和失败状态。
- 已实现：消费者查询 Inbox、成功或失败记录、重试队列和死信处理。
- 已实现：申请、发券、核销等关键业务唯一约束，以及核销乐观锁。
- 当前边界：审核业务事务与 Inbox 成功记录不是同一个事务，存在业务已提交但 Inbox 未记录的故障窗口。
- 答辩时可以提出改进方案，但不能把改进方案说成项目已经实现。
