理解了**持久化**（数据存硬盘）之后，**主从复制（Master-Slave Replication）**是 Redis 走向“高可用”和“高性能”的第二步。

如果说持久化是为了**“丢不了”**，那主从复制就是为了**“坏不了”**和**“跑得快”**。

---

### 1. 核心概念：老板与员工

在 Redis 的主从架构中，角色分工非常明确：

*   **主节点 (Master)：**
    *   **权力：** 既能读，也能**写**（SET, DEL, INCR...）。
    *   **责任：** 当自己有数据变化时，要实时把这些变化“告诉”（同步）给所有的从节点。
*   **从节点 (Slave/Replica)：**
    *   **权力：** 默认只能**读**（GET, HGET...），不能写。
    *   **责任：** 时刻紧跟 Master，保证自己手里的数据和 Master 一模一样。

#### 为什么要这么干？
1.  **读写分离（性能）：** 互联网应用通常“读多写少”。Master 只负责写，成千上万个读请求分摊给多个 Slave。
2.  **数据冗余（安全）：** Master 的硬盘坏了没关系，Slave 还有一份完整的数据。
3.  **高可用（HA）的基础：** 如果 Master 挂了，我们可以把一个 Slave 临时提拔成 Master，保证业务不中断。

---

### 2. 动手实验：在你的电脑上搭一个“一主一从”

既然你已经有一个名为 `my-redis` 的容器在运行了，我们把它当做 **Master**。现在我们再启动一个容器当 **Slave**。

#### 第一步：启动 Slave 容器
打开你的 Windows 终端（CMD 或 PowerShell），执行下面这行命令：
```bash
docker run -d --name redis-slave --link my-redis:master redis redis-server --replicaof master 6379
```
> **命令解释：**
> *   `--link my-redis:master`: 让这个新容器能通过 `master` 这个名字访问到你的旧容器。
> *   `--replicaof master 6379`: 核心指令！告诉这个 Redis：你启动后要去连接 master 的 6379 端口，认它做老大。

#### 第二步：验证身份
1.  **进入 Master 查看状态：**
    ```bash
    docker exec -it my-redis redis-cli
    info replication
    ```
    *你应该能看到 `role:master`，并且 `connected_slaves:1`。*

2.  **进入 Slave 查看状态：**
    ```bash
    docker exec -it redis-slave redis-cli
    info replication
    ```
    *你应该能看到 `role:slave`，并且 `master_link_status:up`。*

#### 第三步：测试数据同步（神奇的时刻）
1.  **在 Master 写入数据：**
    ```bash
    # 在 my-redis 的窗口输入
    SET boss_msg "Work Hard!"
    ```
2.  **在 Slave 读取数据：**
    ```bash
    # 在 redis-slave 的窗口输入
    GET boss_msg
    ```
    *你会发现，你明明没在 Slave 上写过数据，但它已经同步过来了！*

#### 第四步：测试“只读”限制
1.  **在 Slave 尝试写入：**
    ```bash
    SET slave_msg "I want to rest"
    ```
    *你会收到一个报错：`(error) READONLY You can't write against a read only replica.`*
    *这证明了 Slave 的“员工”身份，它不能私自改动数据。*

---

### 3. 主从同步的底层原理（面试常考）

当你执行 `--replicaof` 的那一刻，发生了什么？

1.  **全量同步（第一次见面）：**
    *   Master 执行 `BGSAVE` 生成一个 **RDB 文件**。
    *   Master 把 RDB 发给 Slave。
    *   Slave 把自己的旧数据清空，加载这个 RDB。
    *   在传 RDB 期间产生的写命令，Master 会存在一个缓冲区（Replication Buffer），等 RDB 传完后再发给 Slave。
2.  **增量同步（日常维护）：**
    *   Master 每执行一个写命令，就异步地把这个命令发给 Slave。
    *   网络波动断开了怎么办？Slave 重连后，会根据一个“偏移量”（Offset）向 Master 索要断开期间缺失的那部分数据（就像断点续传）。

### 4. 思考一个问题：如果 Master 突然“暴毙”了怎么办？

在刚才的实验中，如果你执行 `docker stop my-redis`，你会发现：
*   Slave 依然是 Slave。
*   Slave 依然只能读，不能写。
*   整个系统失去了写能力。

**这就是“主从模式”的一个痛点：** 它无法自动处理故障。

为了解决这个问题，我们需要一个“哨兵”来时刻盯着 Master，一旦发现 Master 没气了，就赶紧投票选出一个新的 Master。

主从复制的配置方式主要有三种：**修改配置文件**（最常用）、**启动参数**（之前实验用的）和**运行中命令**。

既然你问到“配置文件是什么方式”，我们重点拆解 **`redis.conf`** 里的相关配置。

---

### 1. 配置文件的核心参数

在 Redis 5.0 以后，官方将 `slave` 改名为 `replica`（为了更严谨）。在从节点的配置文件里，你主要会看到这几项：

#### 从节点 (Slave) 的关键配置：
```conf
# 1. 认老大：指定主节点的 IP 和 端口
replicaof 127.0.0.1 6379

# 2. 密码授权：如果主节点设置了 requirepass，从节点必须配置这个才能同步
masterauth 123456

# 3. 只读模式：默认是 yes，防止误写导致数据不一致
replica-read-only yes

# 4. 优先级：当主节点挂了，哨兵会根据这个值选新主（值越小优先级越高）
replica-priority 100
```

#### 主节点 (Master) 的相关配置：
主节点通常**不需要**特意配置谁是它的从节点，它只需要关注安全和同步效率：
```conf
# 主节点建议设置密码
requirepass 123456

# 如果从节点数量少于 3 个，或者延迟超过 10 秒，主节点拒绝写入（保护机制，可选）
# min-replicas-to-write 3
# min-replicas-max-lag 10
```

### 2. 动手实验：用配置文件启动“一主一从”

因为你用的是 Docker，我们要把 Windows 上的配置文件“映射”到容器里。

#### 第一步：在你的 Windows 电脑上准备两个文件
找一个文件夹（比如 `D:\redis_test`），创建两个文本文件：

**文件 1：`master.conf`**
```conf
port 6379
# 设置密码，增加点难度
requirepass 123456
```

**文件 2：`slave.conf`**
```conf
port 6380
# 认 6379 当老大（注意：在 Docker 内部网络中，我们要用主容器的名字）
replicaof master_node 6379
# 必须要配密码才能连上 master
masterauth 123456
replica-read-only yes
```

#### 第二步：用 Docker 挂载配置文件启动
1.  **先停掉之前的容器：** `docker stop my-redis redis-slave` 
2.  **启动 Master：**
    ```bash
    # 这里的 D:/redis_test 请换成你实际的路径
    docker run -d --name master_node -v D:/redis_test/master.conf:/usr/local/etc/redis/redis.conf redis redis-server /usr/local/etc/redis/redis.conf
    ```
3.  **启动 Slave：**
    ```bash
    docker run -d --name slave_node --link master_node:master_node -v D:/redis_test/slave.conf:/usr/local/etc/redis/redis.conf redis redis-server /usr/local/etc/redis/redis.conf
    ```

#### 第三步：验证
1.  进入从节点：`docker exec -it slave_node redis-cli -p 6380`
2.  输入 `info replication`。
    *   你会看到 `master_link_status: up`。
    *   如果显示 `down`，说明密码（masterauth）或者网络没配对。

---

### 3. 三种配置方式的对比

| 方式 | 特点 | 适用场景 |
| :--- | :--- | :--- |
| **修改配置文件** | 永久生效，重启不丢失 | **生产环境**的标准做法 |
| **命令行参数** | 启动时指定，无需改文件 | Docker 快速测试（比如我们之前的实验） |
| **运行时命令** | `REPLICAOF IP Port` | 临时改变主从关系，无需重启服务器 |

**技巧提示：**
如果你在 `redis-cli` 里执行了 `REPLICAOF 127.0.0.1 6379`，它立刻就会生效。但如果你想让它重启后依然生效，记得执行一次 **`CONFIG REWRITE`**，Redis 会自动把你刚才输入的命令写进 `.conf` 文件里。

---

### 总结
主从复制的配置其实就是**“从节点主动去贴主节点”**。

**接下来我们要聊的“哨兵模式”，其本质就是：**
当主节点挂了，由一个第三方软件（哨兵）自动登录到从节点的 `redis-cli` 里，帮它执行一句 `REPLICAOF no one`（翻身做主人），并让其他从节点执行 `REPLICAOF 新主人`。
