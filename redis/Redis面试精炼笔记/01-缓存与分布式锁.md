## 1. Redis 缓存适用边界

Redis 适合读取频繁、计算或数据库查询成本较高，并且允许短暂不一致的数据。数据库通常是事实源，Redis 负责加速读取和吸收热点，不能因为 Redis 更快就把它描述成最终正确性的唯一保证。

不宜直接依赖普通缓存解决的场景：

- 必须实时读取最新值、不能接受短暂旧数据；
- 写多读少，缓存维护成本可能高于收益；
- 单条数据过大或访问极少，容易浪费内存；
- 需要跨 Redis 与数据库的绝对原子提交。

## 2. Cache Aside 旁路缓存

### 2.1 读流程

```text
请求读取
→ 查询Redis
→ 命中：直接返回
→ 未命中：查询数据库
→ 数据存在：写入Redis并设置TTL，再返回
→ 数据不存在：按策略缓存短TTL空值或直接返回不存在
```

### 2.2 写流程

```text
更新数据库
→ 删除缓存
→ 后续读取未命中
→ 从数据库加载新值并回填
```

通常选择删除而不是同步更新缓存：

- 缓存可能由多表或复杂计算生成，直接维护容易出错；
- 连续写入但没有读取时，反复更新缓存浪费资源；
- 删除后按需加载，逻辑和故障处理相对简单。

### 2.3 一致性边界

数据库更新与 Redis 删除不在同一个本地事务中，因此 Cache Aside 只能趋向最终一致，不能保证强一致。TTL 是最后过期边界，不是强一致机制。

## 3. 穿透、击穿与雪崩

| 问题 | 触发条件 | 流量特征 | 主要防线 | 关键副作用 |
|---|---|---|---|---|
| 缓存穿透 | 查询数据库中不存在的Key | 相同或大量非法Key反复打到数据库 | 空值、布隆过滤器、校验、限流 | 空值一致性；布隆假阳性；限流误伤 |
| 缓存击穿 | 单个热点Key过期 | 大量请求同时查询同一数据 | 互斥重建、逻辑过期、热点预热 | 等待升高；锁超时；旧值取舍 |
| 缓存雪崩 | 大量Key同时失效或Redis整体不可用 | 大面积请求同时进入数据库 | 随机TTL、多级缓存、高可用、限流降级 | 多副本一致性；降级损失；不能覆盖所有故障 |

记忆：**穿透是数据不存在，击穿是一个热点失效，雪崩是大量缓存一起失效。**

### 3.1 缓存穿透

#### 缓存空值

数据库确认数据不存在后，写入空标记并设置较短 TTL，可挡住相同不存在 Key 的重复请求。

边界：空值占用空间；如果期间创建了真实数据，旧空值可能让用户暂时查不到，需要在创建成功后删除空缓存或等待 TTL。

#### 布隆过滤器

请求先判断 Key 是否可能存在；判断为“一定不存在”时直接拒绝，不查数据库。

边界：布隆过滤器有假阳性，即不存在的数据可能被判断为“可能存在”；普通布隆过滤器删除和数据同步较麻烦。只有在过滤器数据维护正确时，才可以说它没有假阴性。

入口还应配合参数合法性校验、限流和黑名单，不能让 Redis 单独承担恶意流量。

### 3.2 缓存击穿

热点 Key 失效后，大量线程同时未命中并查询数据库。互斥重建的基本链路：

```text
缓存未命中
→ 尝试获取短期锁
→ 获得锁：再次检查缓存 → 查询数据库 → 回填 → 释放锁
→ 未获得锁：短暂等待后重试，或返回旧值/降级结果
```

必须再次检查缓存，避免等待期间已有线程完成回填后仍重复查询数据库。

互斥重建的问题：

- 未获锁请求需要等待，尾延迟会上升；
- 锁过期太短会在重建未完成时失效，仍可能重复重建；
- 锁过期太长会让故障后的等待变长；
- 不能无限自旋，应限制次数并设计降级路径。

逻辑过期可以先返回旧值，再由一个线程异步重建。它提高可用性，但牺牲一段时间的数据新鲜度，只适合允许陈旧读取的场景。

### 3.3 缓存雪崩

防线组合：

- `基础TTL + 随机值`，打散大量 Key 的过期时间；
- 热点数据预热、较长 TTL 或逻辑过期；
- Redis 主从、哨兵或集群等高可用手段；
- 服务入口限流、熔断、降级；
- 必要时使用本地缓存或多级缓存；
- 数据库连接数与并发保护，避免缓存故障拖垮数据库。

随机 TTL 只能缓解集中失效，不能解决 Redis 整体不可用。

## 4. 更新数据库与删除缓存的顺序

### 4.1 为什么不优先“先删缓存，再更新数据库”

```text
线程A删除缓存
→ 线程B缓存未命中，读取数据库旧值
→ 线程A更新数据库
→ 线程B把旧值写回缓存
```

旧值可能保留到 TTL 到期，因此风险较大。

### 4.2 “先更新数据库，再删除缓存”仍有窗口

数据库已提交、缓存尚未删除时，并发请求可能读到旧缓存。此外还存在较少见的窗口：读线程先查到数据库旧值，写线程随后更新数据库并删除缓存，读线程最后把旧值回填。

结论：**先更新数据库再删除缓存通常窗口更小，但仍不是绝对强一致。**

### 4.3 删除缓存失败

```text
数据库更新成功
→ DEL失败
→ 有限次数退避重试
→ 仍失败则记录失效事件，由消息或补偿任务继续删除
→ TTL、监控、对账兜底
```

关键场景可用 Outbox 将数据库业务变更和“缓存失效事件”放入同一个数据库事务，再异步执行删除。延迟双删只能缩小部分并发回填窗口，无法保证第二次删除一定执行，也很难精确决定延迟时间，不能把它描述成强一致方案。

## 5. TTL 决策

| 数据类型 | TTL思路 | 注意事项 |
|---|---|---|
| 普通数据 | 根据更新频率和容忍旧值时间设置 | 太短降低命中率，太长延长陈旧时间 |
| 批量同类数据 | 基础TTL加随机值 | 用于打散过期，不解决Redis宕机 |
| 热点数据 | 较长TTL、预热或逻辑过期 | 必须有主动更新/失效机制 |
| 空值 | 较短TTL | 新建真实数据时应主动清除空值 |

## 6. Redis 分布式锁主干

### 6.1 原子加锁

```redis
SET lock:resource:123 <unique-value> NX PX 30000
```

- `NX`：Key 不存在时才写入；
- `PX`：同时设置毫秒级过期时间，防止持锁进程宕机后永久占锁；
- `unique-value`：UUID 等当前请求唯一所有者标识。

不能使用 `SETNX` 后再单独 `EXPIRE`，因为两条命令之间宕机可能留下没有过期时间的锁。

### 6.2 校验所有权后原子释放

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

如果不校验唯一值，旧持锁者可能误删后来持锁者的锁。不能由应用先 `GET` 再 `DEL`，因为两条命令之间锁可能过期并被其他线程获得；比较和删除必须通过 Lua 原子完成。

### 6.3 过期、续期与业务超时

过期时间避免永久死锁，但业务执行超过 TTL、JVM 暂停、进程调度或网络阻塞都可能让锁提前失效，随后出现两个业务同时执行。

看门狗可以在业务未结束时续期，但续期必须校验所有权，并在业务完成后停止。续期线程也可能暂停或因网络故障失败；业务卡死还可能被不断续期，因此仍需最大执行时间、超时、监控和降级。

### 6.4 主从切换边界

```text
客户端A在主节点获得锁
→ 锁尚未复制到从节点
→ 主节点宕机，从节点提升
→ 客户端B在新主节点再次获得同一把锁
```

此时 A、B 都可能认为自己持锁。因此 Redis 锁只是并发控制手段，不能单独保证业务绝对一致。关键业务还要使用数据库条件更新、`affectedRows`、唯一约束、版本号、状态机和幂等键兜底；要求更高时可考虑 fencing token，让存储层拒绝旧持锁者。

## 7. Lua 额度预占与补偿

Lua 可以在 Redis 服务端原子完成“检查额度 + 扣减额度”，避免普通 `GET` 与 `DECRBY` 之间被其他命令插入。

```lua
local balance = tonumber(redis.call('get', KEYS[1]) or '0')
local amount = tonumber(ARGV[1])

if balance < amount then
    return 0
end

redis.call('decrby', KEYS[1], amount)
return 1
```

Lua 只保证脚本内 Redis 操作的原子执行，不能保证 Redis 扣减与 MySQL 事务原子提交，也不能保证业务失败后的补偿一定成功。MySQL 仍需条件更新、事务和唯一约束作为正确性防线。

### 三个最小测试

| 场景 | 输入 | 预期返回 | 验证 |
|---|---|---|---|
| 预占成功 | 初始10，预占3 | 成功 | 余额为7，业务标识已记录 |
| 余额不足 | 初始2，预占3 | 失败 | 余额仍为2，不产生成功标识 |
| 失败补偿/重复补偿 | 预占成功后模拟MySQL失败 | 首次恢复，重复执行不再增加 | 余额恢复原值，补偿业务键唯一 |

补偿必须以业务流水号做幂等控制；同步补偿仍可能失败，因此需要补偿任务、重试、对账、告警和人工处理边界。

## 8. 面试 60 秒回答

### 8.1 穿透、击穿、雪崩

> 缓存穿透是查询缓存和数据库都不存在的数据，可以使用短TTL空值、布隆过滤器并配合参数校验和限流；空值有一致性成本，布隆有假阳性。缓存击穿是单个热点Key失效后大量请求同时访问数据库，可用互斥重建或逻辑过期，但分别带来等待延迟和旧值问题。缓存雪崩是大量Key同时失效或Redis整体故障，应通过随机TTL、预热、高可用、限流降级和数据库保护组合处理。

### 8.2 Cache Aside 与一致性

> Cache Aside 读时先查缓存，未命中再查数据库并回填；写时通常先更新数据库再删除缓存。先删缓存更容易被并发读把数据库旧值写回，先更新再删除的窗口通常更小，但删除失败和并发回填仍可能产生短暂不一致，所以需要有限重试、消息或补偿、TTL、监控和对账，不能宣称强一致。

### 8.3 分布式锁

> 基本Redis分布式锁使用SET key uniqueValue NX PX原子加锁，释放时用Lua校验所有权后删除。过期时间防止永久死锁，但业务超时、JVM暂停、续期失败、网络故障和主从切换都可能破坏互斥，所以Redis锁不能单独保证业务一致性，最终仍需数据库条件更新、唯一约束和幂等机制兜底。

## 10. 最短关键词链

```text
Cache Aside：先查缓存 → 未命中查库 → 回填+TTL → 更新库后删缓存 → 短暂不一致
穿透：不存在Key → 空值/布隆 → 空值一致性/假阳性
击穿：热点过期 → 互斥重建/逻辑过期 → 等待/旧值
雪崩：大量失效 → 随机TTL/高可用/限流降级
删除失败：有限重试 → 消息或补偿 → TTL/监控/对账
分布式锁：SET NX PX+唯一值 → Lua校验删除 → 超时/续期/主从边界 → 数据库兜底
额度预占：Lua原子检查扣减 → MySQL事务事实源 → 幂等补偿 → 对账告警
```
