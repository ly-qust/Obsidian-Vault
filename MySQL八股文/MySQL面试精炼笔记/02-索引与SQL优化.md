# 索引与 SQL 优化

[[01-InnoDB架构与日志|上一篇：InnoDB]] · [[00-MySQL面试知识地图|知识地图]] · [[03-事务-MVCC与锁|下一篇：事务与锁]]

## 1. 索引的本质

索引用额外空间和写入维护成本，换取更少的数据扫描。InnoDB 常用 B+Tree，因为它树高低、适配数据页、支持等值与范围查询。

> 不能说一次查询一定产生固定次数的磁盘 IO：根节点和中间页可能已在 Buffer Pool 中。

## 2. 聚簇索引与二级索引

![[Pasted image 20260817151832.png|850]]

聚簇索引叶子节点保存完整行数据。InnoDB 优先使用主键；没有主键则选择合适的唯一非空索引，否则生成隐藏行 ID。一张表只有一个聚簇索引。

![[Pasted image 20260817152151.png|850]]

图中的“非聚簇索引”在 InnoDB 面试中通常称为 **二级索引**：叶子节点主要保存二级索引列和主键值。

```text
二级索引找到主键
→ 再访问聚簇索引
→ 取得其他列
```

第二次访问称为回表。

## 3. 覆盖索引与 ICP

覆盖索引：查询需要的列都能从某个索引中取得，通常不需要常规回表。

```sql
CREATE INDEX idx_user_status ON application(user_id, status);

SELECT id, user_id, status
FROM application
WHERE user_id = 1;
```

InnoDB 二级索引还包含主键 `id`，上述查询可能被覆盖，`Extra` 常见 `Using index`。

ICP（索引条件下推）：存储引擎先利用索引中的条件过滤，减少回表次数；它不等于覆盖索引，`Extra` 常见 `Using index condition`。

## 4. 联合索引与最左前缀

联合索引 `(a,b,c)` 先按 `a` 排序，`a` 相同时按 `b`，再按 `c`。

```text
通常可精准定位：a；a,b；a,b,c
通常不能直接依赖：仅 b；仅 c
```

注意：

- WHERE 书写顺序通常不决定索引匹配，优化器会重排条件；
- 缺少中间列时，前面的列仍可能生效，后面的列不一定能继续定位；
- 范围条件后的列通常不能继续缩小索引扫描区间，但仍可能用于 ICP、过滤或覆盖；
- MySQL 8.0 可能使用 skip scan 等优化，不能把“最左匹配”背成绝对失效规则。

## 5. 索引设计

```text
真实高频 SQL
→ 等值过滤
→ 范围条件
→ 关联、排序、分组
→ 返回列与覆盖
→ 写入成本
→ EXPLAIN / 实际耗时验证
```

原则：

- 优先服务高频且重要的真实 SQL；
- 等值过滤列通常在前，再考虑范围、排序和覆盖；
- 字段顺序还要结合选择性和数据分布；
- 使用唯一约束守住业务不变量；
- 避免重复或高度重叠索引；
- 主键宜窄、稳定，近似递增通常有利；随机宽主键易增加页分裂和二级索引体积，但不能绝对说 UUID 禁用。

常见索引效果差的原因：

- 未满足有效的联合索引前缀；
- 对索引列计算或函数处理；
- 隐式类型转换；
- `LIKE '%abc'` 前导模糊匹配；
- 选择性差或返回数据过多；
- `OR` 分支缺少合适索引；
- 优化器判断全表扫描成本更低。

## 6. EXPLAIN

判断顺序：

```text
type → key → rows / filtered → Extra → EXPLAIN ANALYZE
```

| 字段 | 含义 |
|---|---|
| type | 访问方式 |
| key | 实际选择的索引；非空不代表一定快 |
| key_len | 计划使用的索引键最大字节长度，不能机械换算为列数 |
| rows | 预计检查行数，不是最终返回行数 |
| filtered | 预计过滤后保留比例 |
| Extra | 覆盖、过滤、排序、临时表等信息 |

常见 `type`：

```text
const > eq_ref > ref > range > index > ALL
```

这只是常见参考顺序。小表 `ALL` 可能合理，`range` 扫描大量数据也可能很慢。

| Extra | 含义 |
|---|---|
| Using index | 覆盖索引 |
| Using index condition | ICP，仍可能回表 |
| Using where | 还需按 WHERE 条件过滤 |
| Using filesort | 需要额外排序，不等于一定写磁盘 |
| Using temporary | 使用临时表 |

`EXPLAIN` 主要给估算计划；`EXPLAIN ANALYZE` 会实际执行并给出真实行数、循环和耗时，生产环境慎用。

## 7. 慢 SQL 排查

```text
慢查询日志/监控发现 SQL
→ 拿到真实参数、频率、返回量
→ EXPLAIN / EXPLAIN ANALYZE
→ 看扫描、回表、排序、临时表
→ 看锁等待、IO、Buffer Pool、CPU
→ 优化 SQL/索引后复测
```

常见工程优化：

- 避免无意义的 `SELECT *`；
- 批量操作代替大量单条写入；
- 深分页使用稳定游标条件，例如 `WHERE id > ? ORDER BY id LIMIT 20`；
- 不要见慢 SQL 就加索引，慢也可能来自锁等待、网络和返回数据过多。

## 8. 面试标准回答

> 我分析索引时不会只看有没有走索引，而是先看 SQL 的过滤、排序和返回列，再结合 EXPLAIN 的 type、key、rows、filtered、Extra 判断扫描范围、回表、排序和临时表。InnoDB 聚簇索引叶子节点保存完整行，二级索引保存索引列和主键；查询列都在索引中就是覆盖索引。联合索引遵循有序前缀，但字段顺序要结合等值、范围、选择性和排序，最后用真实数据验证。
