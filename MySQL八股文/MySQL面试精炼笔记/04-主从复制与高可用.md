# 主从复制与高可用

[[03-事务-MVCC与锁|上一篇：事务与锁]] · [[00-MySQL面试知识地图|知识地图]] · [[05-高频面试速记与自测|下一篇：速记]]

## 1. 复制链路

```mermaid
flowchart LR
    A[主库事务提交] --> B[binlog]
    B --> C[主库 dump 线程]
    C --> D[从库 I/O receiver 线程]
    D --> E[relay log]
    E --> F[SQL / applier 线程]
    F --> G[从库数据]
```

标准流程：

```text
主库记录 binlog
→ dump 线程向从库发送事件
→ 从库 I/O 接收线程写 relay log
→ 从库 applier 线程重放事务
```

GTID 为每个已提交事务提供全局标识，相比手工维护 binlog 文件和位置，更便于复制管理和故障切换。

## 2. 复制延迟

MySQL 传统复制具有异步特征：主库提交成功时，从库不一定已经应用完成。

常见原因：

- 大事务或主库短时间写入过快；
- 从库执行能力不足；
- 缺少索引导致从库重放慢；
- 网络抖动；
- 长查询、锁等待或磁盘压力；
- 并行复制能力没有充分利用。

## 3. 读写分离的一致性问题

```text
客户端写主库成功
→ 立即读从库
→ 从库尚未重放
→ 读不到刚写的数据
```

常见策略：

- 写后的一段时间内读主库；
- 强一致业务固定读主库；
- 等待从库追上指定 GTID/位点后再读；
- 监控延迟，延迟过大时摘除从库；
- 接受最终一致性的业务再走从库。

## 4. 高可用边界

- 异步复制性能好，但主库突然故障时可能丢失尚未传到从库的事务；
- 半同步复制降低丢失窗口，但会增加提交延迟，也不等于所有从库都已执行完成；
- 自动故障切换需要选主、健康检查、路由切换和脑裂防护；
- 复制解决副本与扩展问题，不等于备份；误删除可能被同步到所有副本，仍需全量备份和 binlog 恢复能力。

## 5. 面试标准回答

> MySQL 主从复制以 binlog 为基础。主库 dump 线程发送 binlog 事件，从库 I/O 接收线程写入 relay log，再由 applier 线程重放。传统复制具有异步特征，因此读写分离可能出现写后立刻读不到的问题，强一致读可以走主库或等待从库追上指定进度。GTID 能简化复制定位和故障切换，但复制不等于备份，高可用还需要选主、路由、监控和脑裂防护。
