## 一、它解决什么实际问题

一句话：**EXPLAIN 让你看到优化器"打算怎么执行这条 SQL"，而不是瞎猜。**

写 SQL 时你以为的执行路径，和 MySQL 实际走的路径，经常不是一回事。EXPLAIN 就是把优化器的决策摊开给你看：

- 走没走索引？走了哪个索引？
- 是全表扫描还是索引扫描？
- 有没有用到覆盖索引？
- 大概要扫多少行？
- 有没有 filesort / temporary 这种重操作？

**典型使用场景**：慢 SQL 排查、索引是否生效验证、联合索引列顺序调优、分页深翻页分析。

## 二、五个字段先看什么（优先级排序）

按"对性能影响从大到小"排：

|优先级|字段|看什么|危险信号|
|---|---|---|---|
|1|**type**|访问类型，决定扫描效率|`ALL`（全表扫描）、`index`（全索引扫描）基本要优化|
|2|**key**|实际用了哪个索引|`NULL` = 没走索引；和你预期的索引不一致|
|3|**rows**|预估扫描行数|数字远大于实际返回行数，说明过滤性差|
|4|**Extra**|附加信息|`Using filesort`、`Using temporary`、`Using where` 需关注|
|5|**key_len**|索引使用了多少字节|联合索引中判断用到了前几列|

### type 从好到差的记忆口诀

> **system > const > eq_ref > ref > range > index > ALL**

面试常考的三个：

- **const**：主键/唯一索引等值查询，最多一行
- **ref**：非唯一索引等值查询
- **range**：索引范围查询（`>`、`<`、`IN`、`BETWEEN`）
- **ALL**：全表扫描，性能最差

### Extra 三个关键值

- **Using index**：覆盖索引，不需要回表 ✅
- **Using where**：存储引擎层返回行后，Server 层再过滤（说明索引没完全过滤掉）
- **Using filesort**：排序没用上索引，额外排序 ⚠️
- **Using temporary**：用了临时表（GROUP BY / DISTINCT 常见）⚠️

## 三、最容易踩的坑

### 坑 1：EXPLAIN 看到的 ≠ 实际执行的

EXPLAIN 是**预估**，`rows` 是统计信息估算的，不是真实行数。统计信息过期时偏差很大。

> 解决：`ANALYZE TABLE` 更新统计信息；或用 `EXPLAIN ANALYZE`（MySQL 8.0.18+）看真实执行耗时。

### 坑 2：key 显示用了索引，但其实几乎全扫

`type=range` 但 `rows` 巨大，说明范围太宽，跟全表扫描差不多。索引"名义上用了"，实际没加速。

### 坑 3：Extra 里的 Using filesort 不代表一定用了文件排序

`filesort` 名字误导人——它可能在内存里排（sort buffer），不一定写磁盘。但仍然是额外开销，能靠索引避免就避免。

### 坑 4：EXPLAIN 看不到的东西

- 实际执行时间（普通 EXPLAIN 不执行 SQL）
- 锁等待、IO 延迟
- 触发器、存储过程内部逻辑

### 坑 5：联合索引中 key_len 才是"用了几列"的真相

`key=idx_status_campaign_time` 不代表三列都用了。算 `key_len`：

- `status` 是 varchar → 看字符集和长度
- `campaign_id` int → 4 字节
- `create_time` datetime → 5 字节（8.0 后）

key_len 只够前两列 = 第三列没用于定位，只可能用于覆盖。

## 四、如果让我设计一个替代方案，我会怎么改

EXPLAIN 的根本问题是：**它给的是"计划"，不是"结果"；给的是"字段"，不是"建议"。**

如果重新设计，我会做这几件事：

### 1. 默认输出"实际执行"而非"预估计划"

现在 EXPLAIN 不跑 SQL，给的是估算。应该默认像 `EXPLAIN ANALYZE` 一样实际执行，返回：

- 每个算子的**真实耗时**
- **真实扫描行数** vs 预估行数（偏差一目了然）
- 回表次数、排序行数等真实指标

### 2. 直接给出"问题诊断 + 优化建议"，而不是原始字段

现在要人工解读 `type=ALL, rows=1000000` 意味着什么。替代方案应该直接输出：

```
⚠️ 全表扫描，预计扫描 100w 行
   建议：在 campaign_id 上建立索引，或调整联合索引列顺序
   预估收益：扫描行数降至 ~200，耗时降低 99%
```

把"解读成本"从用户转移到工具。

### 3. 可视化执行计划，而非表格

用树形/火焰图展示每个算子的耗时占比，一眼看出瓶颈在哪。类似 PostgreSQL 的 `EXPLAIN (ANALYZE, BUFFERS)` + 可视化工具。

### 4. 增加"对比模式"

输入两条等价 SQL（或加索引前后），直接对比执行计划差异和预估成本变化。现在要人工跑两次、人工对比。

### 5. 暴露"为什么选这个计划"

优化器是黑盒，只告诉你结果不告诉你原因。替代方案应该输出：

- 候选索引有哪些
- 每个候选的预估成本
- 为什么选了 A 没选 B（统计信息依据）

这样排查"索引为什么没走"时不用猜。

---

## 五、90 秒总结（面试版）

> EXPLAIN 的核心价值是**把优化器的执行决策可视化**，解决"SQL 慢但不知道慢在哪"的问题。五个字段里先看 type 判扫描方式、再看 key 确认索引、rows 看扫描规模、Extra 看有没有额外排序/临时表/回表。它最大的坑是给的是预估不是实际、字段需要人工解读、filesort 名字误导。如果重新设计，我会让它默认实际执行返回真实耗时、直接输出诊断和建议而不是原始字段、用可视化替代表格、增加索引选择的可解释性——本质上是从"给原始数据"转向"给结论"。
