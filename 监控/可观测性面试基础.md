# 可观测性面试基础

## 一句话结论

可观测性用 Metrics 看趋势和告警、Logs 看事件细节、Trace 看一次请求跨组件的完整链路；排障时三者要用 trace_id、时间窗口和请求特征串起来。

## 因果链

```text
用户感知超时 / 失败
→ 指标确认影响范围和时间趋势
→ 日志定位错误类型与上下文
→ Trace 定位慢在哪个 Span
→ 检查数据库、Redis、RabbitMQ、外部 API 等依赖
→ 修复后观察恢复指标并补充告警
```

## Metrics、Logs、Trace

| 类型 | 主要回答 | 典型字段 |
|---|---|---|
| Metrics | 是否变慢、变多、变满？趋势如何？ | QPS、延迟、错误率、CPU、内存、队列积压 |
| Logs | 哪一次请求发生了什么？ | 时间、级别、trace_id、业务键、错误原因 |
| Trace | 一次请求经过哪些组件？瓶颈在哪个 Span？ | TraceId、SpanId、父子关系、耗时、状态 |

- Metrics 适合聚合和告警，不适合记录每个用户的完整详情。
- Logs 要结构化、可检索并脱敏；不要把密码、Token、API Key 和完整隐私信息写入日志。
- Trace 把入口、数据库、缓存、MQ 和外部 API 的 Span 串起来；采样要在成本与排障价值之间平衡。
- `trace_id` 只是关联键，不等于自动拥有完整 Trace；上下游都要正确传递并记录。

## Prometheus Pull 与 Grafana 基础

```text
应用暴露 /actuator/prometheus 等指标端点
→ Prometheus 按 scrape 配置定时 Pull
→ Prometheus 保存时间序列
→ PromQL 查询趋势和聚合
→ Grafana 展示 Dashboard
→ 告警规则判断持续异常并通知
```

- Pull 模式下 Prometheus 主动抓取目标，目标短暂不可达时会体现为抓取失败；要监控 scrape 成功率和目标可达性。
- 标签用于按服务、实例、接口等维度聚合；不要把 userId、订单号等高基数字段直接作为标签。
- Grafana 负责查询和展示，不能代替指标采集、日志系统或 Trace 系统。
- 告警应写清阈值、持续时间、影响对象、处理链接和恢复条件；单点瞬时尖峰不一定需要告警。

## Java / SmartRenew 关联

- SmartRenew 的 `application.yml` 暴露 `health`、`info`、`prometheus` 管理端点，说明应用指标入口已预留；是否接入完整 Prometheus/Grafana 环境仍要以部署配置核对。
- AI 链路中的 `AiChatExecutionTrace`、`AiChatLogRecorder` 记录 route、检索命中、模型调用、耗时、tokens、fallback、状态和 trace_id，可用于按请求排障。
- RabbitMQ 重点看队列积压、消费者状态、重试和死信；Redis 重点看内存、连接、命令延迟和缓存命中率；MySQL 重点看慢 SQL、连接池、锁等待和错误率。

## 常用排障指标

| 场景 | 先看什么 | 再查什么 |
|---|---|---|
| 接口变慢 | p95/p99 延迟、错误率、吞吐 | Trace 慢 Span、线程池、DB/Redis/MQ/外部 API |
| Java 服务异常 | 5xx、JVM 堆、GC、线程池、连接池 | 应用日志和具体 Trace |
| RabbitMQ 消费变慢 | ready/unacked、消费者数、重试/死信 | 消费者日志、下游数据库和处理耗时 |
| Redis 异常 | 内存、命中率、连接、延迟、热 Key | 大 Key、淘汰、网络和实例负载 |
| AI 调用失败 | 模型请求数、超时、429、fallback 比例 | provider、model、request_id、trace_id 和知识库命中 |

## 容易答错

- “监控 CPU 就够了”：CPU 正常时也可能有线程池、连接池、队列或外部依赖故障。
- “日志越多越好”：无结构、无 trace_id 或包含敏感信息的日志会增加成本和风险。
- “Prometheus 负责所有可观测性”：它主要是指标采集与查询，Logs 和 Trace 是不同信号。
- “告警阈值越多越好”：应关注可行动性、持续时间和恢复，减少噪声。
- “TraceId 等于用户身份”：TraceId 是一次链路关联标识，权限和用户身份仍由认证上下文负责。

## 高频面试回答

> 我会用 Metrics 发现趋势和影响范围，用 Logs 定位错误事件，用 Trace 还原一次请求跨服务的耗时链路。Prometheus 可以按 Pull 模式抓取应用暴露的指标，Grafana 用于查询和展示。排查 Java 接口时先看错误率和 p95/p99，再按 trace_id 查看日志和慢 Span，最后检查数据库、Redis、RabbitMQ 或外部模型依赖。告警要有阈值、持续时间、恢复条件和处理动作，标签不能放高基数业务 ID。
