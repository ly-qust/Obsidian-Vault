### 1. 线程池 (ThreadPoolExecutor)：服务器的“稳压器”

#### ❌ 为什么不能手动 new Thread()？

在政务系统中，假设早上 9:00 放号，瞬间有 1 万人点击。如果你在代码里写 new Thread(() -> { ... }).start()：

- **内存耗尽：** 每个线程默认占用约 1MB 栈内存。1 万个线程就是 10GB，直接导致 OutOfMemoryError（OOM）。
    
- **切换开销：** CPU 核心数是有限的（通常 8 或 16 核）。1 万个线程在 CPU 上频繁切换（上下文切换），会导致 CPU 100% 但几乎没干活。
    
- **不可控：** 你无法限制同时运行的线程数，系统会像脱缰的野马，瞬间宕机。
    

#### ✅ 线程池如何保护系统？

线程池就像政务大厅的**办事窗口**：

- **核心线程 (Core Threads)：** 常设窗口，一直有人值守。
    
- **阻塞队列 (Work Queue)：** 办事大厅的**排队区**。如果窗口满了，市民先在椅子上坐着等。
    
- **最大线程 (Max Threads)：** 临时窗口。如果排队区也满了，赶紧加开临时窗口。
    
- **拒绝策略 (Rejection Policy)：** 如果连排队区和临时窗口都挤爆了，保安（系统）直接告诉后来的市民：“今日人已满，请明天再来。”
    

**政务系统建议：** 设置一个合理的阻塞队列长度（如 1000），超过后通过拒绝策略返回“系统繁忙”，从而保护核心数据库不被压跨。






### Java 线程池模拟：政务预约并发处理

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class AppointmentSystemPool {

    public static void main(String[] args) {
        // 记录成功处理的请求数
        AtomicInteger successCount = new AtomicInteger(0);

        // 1. 创建自定义线程池 (模拟政务办事大厅)
        ExecutorService threadPoolExecutor = new ThreadPoolExecutor(
                3,                      // 1. corePoolSize: 核心窗口数 (常设3个窗口)
                5,                      // 2. maximumPoolSize: 最大窗口数 (繁忙时临时加到5个)
                1L,                     // 3. keepAliveTime: 临时窗口空闲多久后关闭
                TimeUnit.SECONDS,       // 4. unit: 时间单位 (秒)
                new LinkedBlockingQueue<>(10), // 5. workQueue: 等待区 (大厅排队椅子只有10把)
                Executors.defaultThreadFactory(), // 6. threadFactory: 窗口工作人员的创建工厂
                new ThreadPoolExecutor.AbortPolicy() // 7. handler: 拒绝策略 (排队椅子也满了，直接告诉市民明天再来)
        );

        System.out.println("--- 政务预约系统启动：当前常设窗口3个，排队位10个 ---");

        // 模拟瞬间涌入 20 个市民点击“预约疫苗”
        for (int i = 1; i <= 20; i++) {
            final int citizenId = i;
            try {
                // 提交任务
                threadPoolExecutor.execute(() -> {
                    try {
                        System.out.println(Thread.currentThread().getName() + " 正在为市民 [" + citizenId + "] 办理预约...");
                        // 模拟办理业务耗时 500 毫秒
                        Thread.sleep(500); 
                        successCount.getAndIncrement();
                        System.out.println("✔ 市民 [" + citizenId + "] 预约成功！");
                    } catch (InterruptedException e) {
                        e.printStackTrace();
                    }
                });
            } catch (RejectedExecutionException e) {
                // 触发拒绝策略时的逻辑
                System.err.println("❌ 警告：系统已满！市民 [" + citizenId + "] 无法进入大厅，预约失败。");
            }
        }

        // 关闭线程池
        threadPoolExecutor.shutdown();
        
        // 等待所有任务完成
        try {
            if (threadPoolExecutor.awaitTermination(1, TimeUnit.MINUTES)) {
                System.out.println("\n--- 业务办理结束 ---");
                System.out.println("今日成功办理人数: " + successCount.get());
            }
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
    }
}
```

### 🧠 深度解析：这 20 个请求是怎么被处理的？

在你的代码配置下（3个核心，5个最大，10个队列），处理顺序如下：

1.  **前 3 个市民 (1-3号)：** 发现有常设窗口，直接**立即办理**（核心线程）。
2.  **接下来的 10 个市民 (4-13号)：** 窗口满了，被安排到**椅子上坐着排队**（进入 `LinkedBlockingQueue`）。
3.  **再接下来的 2 个市民 (14-15号)：** 窗口满了，排队椅子也坐满了，大厅赶紧**加开 2 个临时窗口**（达到 `maximumPoolSize` 5个）。
4.  **最后的 5 个市民 (16-20号)：** 窗口 5 个全满，椅子 10 把全满。系统触发**拒绝策略**（`AbortPolicy`），直接报错，预约失败。

---

### 💡 为什么这对“高并发政务系统”至关重要？

*   **防止崩溃：** 如果不设 `maximumPoolSize` 和队列上限，1 万个请求会瞬间开启 1 万个线程，你的服务器内存会立马溢出（OOM），导致整个政务系统宕机。
*   **流量削峰：** 通过 `LinkedBlockingQueue`（排队椅子），系统可以用稳定的速度处理请求，而不是被瞬间洪峰冲垮。
*   **用户反馈：** 拒绝策略（`AbortPolicy`）能让系统优雅地告诉用户“当前太忙”，而不是让用户在那里转圈圈等待几分钟后看到一个 502 报错。

### 🎓 课后小练习：
你可以试着把代码里的 `AbortPolicy` 换成 `CallerRunsPolicy`（让市民自己去办，即在主线程执行）。你会发现，虽然没人被拒绝了，但系统运行的速度明显变慢了。这就是**高并发调优**的起点。
