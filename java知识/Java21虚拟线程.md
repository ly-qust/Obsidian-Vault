Java 21 将 **虚拟线程（Virtual Threads）** 正式纳入 Java SE。它由 JDK 提供，适合提高高并发 I/O 场景的吞吐；不会让单个 CPU 密集型任务自动变快。

以下内容用于理解背景、原理、用法和边界。具体性能必须结合任务类型、JDK、操作系统和下游资源压测。

> [!warning] 这是一份原始资料的纠错版
> 文中固定的内存大小、线程数量、纳秒级开销、“所有阻塞都能卸载”和“所有 synchronized 都应替换”等说法不能作为标准答案。Java 21 的正式行为以 JEP 444 和 Java SE 21 API 为准。

---

### 1. 为什么需要虚拟线程？（核心痛点）

在 Java 21 之前，`java.lang.Thread` 是**平台线程（Platform Thread）**，它是对操作系统（OS）线程的简单包装。

*   **平台线程的局限性：**
    1.  **资源昂贵：** 创建平台线程需要操作系统线程、栈空间等资源，实际开销取决于操作系统、JVM 和配置；平台线程的调度也由操作系统参与。
    2.  **数量有限：** 可创建数量受内存、操作系统和应用配置约束，不能背固定数量。
    3.  **阻塞浪费：** 在传统的“一个线程处理一个请求（Thread-per-request）”模型中，如果线程在等待数据库查询或网络 I/O，这个珍贵的系统线程就会被挂起，造成 CPU 资源闲置。

为了解决这些问题，以前我们不得不采用**响应式编程（Reactive Programming，如 WebFlux）**，但其代码维护成本极高（Callback hell、难以调试）。

---

### 2. 什么是虚拟线程？

虚拟线程是**轻量级**的线程，由 **JVM 调度**而非操作系统调度。

*   **轻量：** 虚拟线程的栈和调度状态按需占用堆等资源，因此可以创建远多于平台线程的虚拟线程；实际并发仍受内存、CPU 和外部资源限制，不能背固定字节数或数量。
*   **廉价：** 创建和销毁的开销极小。
*   **M:N 调度：** 多个虚拟线程运行在少量的平台线程（称为 **载体线程 Carrier Thread**）之上。

---

### 3. 工作原理：挂起与恢复

虚拟线程的关键点在于它如何处理**阻塞**操作。

1.  **挂起（Mounting）：** 当虚拟线程开始执行时，JVM 会将其“挂载”到一个平台线程（载体线程）上。
2.  **卸载（Unmounting）：** 对于 JDK 支持的阻塞 I/O 或可 parking 的等待场景，运行时可以保存虚拟线程状态并将其从载体线程上“卸载”；并非所有阻塞调用都能卸载。
3.  **复用：** 此时，底层的平台线程变空闲了，可以去运行其他的虚拟线程。
4.  **恢复：** 当阻塞操作完成，JVM 会重新将该虚拟线程的状态加载到某个可用的平台线程上继续执行。

**结论：** 开发者可以保留同步阻塞风格；在支持的阻塞场景下，运行时通过挂起虚拟线程来释放载体线程，但这不等于所有代码都变成异步非阻塞。

---

### 4. 如何使用虚拟线程？

Java 21 提供了非常简单的 API 来使用虚拟线程。

#### A. 直接创建
```java
Thread vThread = Thread.ofVirtual().start(() -> {
    System.out.println("Hello from Virtual Thread: " + Thread.currentThread());
});
```

#### B. 使用 ExecutorService (推荐方式)
这是最常用的场景，配合 `try-with-resources` 使用：
```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> {
        // 执行耗时 I/O 任务
        return "result";
    });
} // 自动关闭并等待任务完成
```

#### C. 工厂方法
```java
ThreadFactory factory = Thread.ofVirtual().factory();
factory.newThread(runnable).start();
```

### 5. 关键特性与差异

| 特性 | 平台线程 (Platform Thread) | 虚拟线程 (Virtual Thread) |
| :--- | :--- | :--- |
| **管理方式** | 操作系统管理 | JVM 管理 |
| **内存占用** | 受 JVM、操作系统和启动参数影响，通常更高 | 栈和调度状态按需占用堆等资源 |
| **调度与切换** | 依赖操作系统调度，具体成本需测量 | 由 JVM 调度到载体线程，等待场景通常更有伸缩性 |
| **并发数量** | 受平台线程和资源容量约束 | 通常可远多于平台线程，但仍受堆、CPU 和下游资源约束 |
| **适用场景** | CPU 密集型任务 | I/O 密集型任务 |

---

### 6. 避坑指南与最佳实践（重要）

虽然虚拟线程很强大，但它的用法与传统线程有显著区别：

#### 1. 不要池化（Don't Pool）
*   **传统思维：** 创建线程很贵，所以用 `ThreadPoolExecutor` 复用。
*   **虚拟线程思维：** 虚拟线程本身不应作为昂贵资源放入线程池，通常按任务创建、按生命周期结束；如果要限制数据库、HTTP 服务等稀缺资源，应使用连接池、`Semaphore` 等专门机制。

#### 2. 避免 Pinning（内核钉住）
在以下两种情况下，虚拟线程无法从平台线程中卸载，会导致载体线程被阻塞：
*   **`synchronized` 块/方法：** Java 21 中，如果虚拟线程在 monitor 临界区内执行阻塞操作，可能被“钉”在载体线程上。
    *   **解决方案：** 只对频繁且可能长时间阻塞的临界区评估 `ReentrantLock`；不要机械替换保护纯内存短临界区的 `synchronized`。
*   **Native 方法：** 在 native/foreign function 中发生阻塞时，可能使虚拟线程固定在载体线程上。

#### 3. 限制并发资源
*   **过去：** 通过线程池大小（如 max=50）来限制数据库连接并发。
*   **现在：** 即使可以创建大量虚拟线程，也不能绕过数据库连接数、限流和下游容量。
*   **解决方案：** 使用 **Semaphore（信号量）** 来限制对稀缺资源的访问并发数。

#### 4. ThreadLocal 的使用
Java 21 的虚拟线程支持线程局部变量；如果每个虚拟线程都保存大量 `ThreadLocal` 数据，堆内存仍会增长。应控制数据大小和生命周期，不能把 `ThreadLocal` 当作无限容量上下文。

---

### 7. 虚拟线程 vs 响应式编程 (WebFlux)

*   **响应式编程：** 性能高，但代码是碎片的、难以阅读、堆栈跟踪（Stack Trace）极其混乱。
*   **虚拟线程：** 在适合 I/O 等待的场景中，可以用同步阻塞风格获得接近异步模型的可扩展性；是否达到相近吞吐量必须实测。
*   **结论：** 虚拟线程降低了部分高并发 I/O 服务的编程复杂度，但不替代非阻塞 API、限流、连接池和容量规划。

### 总结

Java 21 的虚拟线程并不是让单个任务运行得更快，而是减少大量等待型任务对平台线程的占用，从而提高合适 I/O 场景下的并发承载能力。是否提升吞吐仍取决于任务类型、JDK 实现、下游容量和实际压测结果。


要理解虚拟线程，确实需要先打通 **操作系统（OS）**、**JVM** 以及 **传统并发模型** 之间的底层逻辑。

下面按 5 个基础知识点说明虚拟线程的执行模型和适用边界。

---

### 1. 操作系统线程：重量级的“打工人”
在 Linux/Windows 等操作系统中，线程是 CPU 调度的最小单位。
*   **1:1 模型：** 平台线程通常与操作系统线程一一对应；虚拟线程则由 JVM 调度到平台线程上执行。
*   **代价高昂：**
    *   **内存开销：** 平台线程的栈、调度和创建成本通常高于虚拟线程，但具体大小受 JVM、操作系统和启动参数影响，不能按固定 1MB 或固定线程数估算。
    *   **创建与调度成本：** 平台线程涉及操作系统调度，创建和切换成本通常更高；具体差异需要以目标环境基准测试为准。

### 2. 用户态 vs 内核态（Context Switch）
这是高并发性能的“杀手”。
*   **内核态：** 只有操作系统内核才有权访问硬件资源（如磁盘、网卡）。
*   **用户态：** 你的 Java 代码运行的地方。
*   **上下文切换（Context Switch）：**
    当一个线程在执行时，由于时间片到了或者遇到了 I/O 阻塞，操作系统需要：
    1.  保存当前线程的 CPU 寄存器信息、程序计数器等。
    2.  切换到内核模式。
    3.  载入另一个线程的数据。
    **结论：** 线程越多、切换越频繁，调度和内存压力越明显；不要把开销写死成某个时间单位，应以实际环境测量。

### 3. I/O 阻塞：最大的资源浪费
绝大多数 Java 应用（如 Spring Boot 业务开发）都是 **I/O 密集型**，而不是 CPU 密集型。
*   **场景：** 你的线程发起一个数据库查询（SQL）或调用一个微服务。
*   **痛点：** 数据库返回数据需要一段时间时，平台线程可能在等待期间保持占用；等待成本受线程实现、JDK、驱动和调用方式影响。
*   **结果：** 线程池里的线程很快被占满。为了支撑更高并发，你不得不增加线程数，但线程越多，内存和上下文切换的压力就越大。

### 4. 线程池（Thread Pool）的本质：无奈的折中
为什么我们要用 `ExecutorService` 线程池？
*   因为创建线程太贵，所以我们提前创建好一批（比如 200 个），循环使用。
*   **局限性：** 固定大小线程池会限制同时执行的任务数。如果工作线程都在等待数据库返回，新请求可能排队；吞吐上限还会受到队列、连接池和下游服务容量影响。

### 5. 响应式编程（Reactive Programming）：痛苦的进化
为了解决上述“线程在 I/O 等待时浪费资源”的问题，业界出现了 WebFlux、RxJava、Vert.x。
*   **原理：** 线程提交 I/O 后，通过回调、事件或其他异步机制在就绪时继续处理。
*   **代价：** 异步代码的控制流、调试和错误传播可能更复杂，但复杂度取决于框架、抽象方式和团队实践。

---

### 现在，我们把这些知识点和【虚拟线程】串起来：

虚拟线程的设计目标是：让 thread-per-task 风格的代码能够承载更多等待型任务，同时由 JVM 管理任务与平台线程之间的映射。

1.  **JVM 调度：** 虚拟线程不是 1:1 对应系统线程，而是由 JVM 调度到平台线程上执行。
2.  **极度廉价：**
    *   它的栈和调度状态按需占用堆等资源，但实际数量仍受堆、CPU、连接池和下游服务容量约束。
    *   可以创建远多于平台线程的虚拟线程，但不能据此保证任意数量都能稳定运行。
3.  **智能挂起（关键点）：**
    *   对于 JDK 支持的阻塞 I/O 或 parking 等待点，运行时可以让虚拟线程暂时暂停。
    *   **重点：** 在可卸载场景，运行时保存虚拟线程状态，并将其从载体平台线程上卸载。
    *   载体平台线程可以继续运行其他已就绪的虚拟线程，但具体调度仍由 JVM 和操作系统共同影响。
    *   等待条件满足后，虚拟线程会恢复并重新挂载到可用的载体线程上；第三方阻塞调用不能一概而论。

### 总结
*   **平台线程模型：** 常见做法是用有限的平台线程处理任务；线程在等待 I/O 时可能持续占用执行资源。
*   **虚拟线程模型：** 可以用 thread-per-task 的方式为任务分配虚拟线程；在支持的等待点，虚拟线程可从载体线程卸载，让载体继续执行其他任务。

**更准确的结论是：Java 21 虚拟线程适合以 thread-per-task 方式承载大量 I/O 等待；它不消除阻塞成本，也不替代对 CPU、连接池和下游容量的控制。**



下面把这个过程按执行阶段拆开说明。

### 1. 这个过程叫“挂载 (Mount)”与“卸载 (Unmount)”

你说系统线程“不用一直等待，发送完立即去帮助下一个”，在 Java 21 中是这样实现的：

*   **执行中（Mounting）：** 当代码在虚拟线程中运行时，JVM 会把它调度到平台线程（称为 **载体线程 Carrier Thread**）上执行。
*   **遇到阻塞（Unmounting）：**
    1.  对于 JDK 支持的阻塞 I/O 或 parking 等等待点，平台线程可能无需长期被占用。
    2.  运行时会保存虚拟线程的执行状态，并在条件满足时暂停或恢复它；不能把所有 `InputStream.read()` 或第三方阻塞调用都概括为同一种行为。
    3.  在可卸载的等待场景，虚拟线程会从载体线程上**卸载（Unmount）**。
*   **切换（Switching）：**
    1.  系统线程现在“自由”了。它不会被销毁，而是立即去运行队列里抓取另一个处于“就绪状态”的虚拟线程来执行。
    2.  挂载/卸载由 JVM 调度器完成，但具体实现和开销不能写死成“纯用户态”或“纳秒级”；载体平台线程仍由操作系统调度。

### 2. I/O 到底是谁在等？（底层黑科技）

你可能会问：“虚拟线程去休息了，系统线程去干活了，那谁在等数据库返回数据呢？”

具体等待机制由 JDK、操作系统和调用类型共同决定；对支持的网络 I/O，运行时可以利用操作系统的异步或多路复用能力。
*   对 JDK 支持的网络 I/O，运行时可以借助操作系统的异步/多路复用能力等待就绪，而不是长期占用载体线程。
*   当等待条件满足，JVM 就会把之前暂停的虚拟线程唤醒，重新挂载到可用的载体线程上，从刚才的位置继续运行。

### 3. 性能提高的本质：从“省时间”到“省空间”

这是一个很常见的误区：**虚拟线程并不会让你的某一段代码跑得更快（Latency），它提高的是系统的吞吐量（Throughput）。**

*   **传统模型：** 平台线程在阻塞 I/O 时仍占用平台线程资源，线程数和下游容量会限制并发。
*   **虚拟线程：** 虚拟线程在支持的等待点可以释放载体线程，因此能提高 I/O 场景的并发承载能力；实际上限仍由堆、CPU、连接池和服务端容量决定。

### 4. 一个形象的比喻：快递员与收件人

*   **传统模型（平台线程）：**
    快递员（系统线程）把件送到你家门口。你（虚拟线程）说：“等等，我找找剪刀拆箱子，还要试穿一下衣服。” 快递员就**一直在门口站着等你**，等了半小时。这段时间他什么也干不了。如果你家这条街有 100 个住户都在试衣服，公司就得派 100 个快递员。

*   **Java 21 模型（虚拟线程）：**
    快递员（载体线程）把件送到你家。你说：“等等，我要试穿。” 快递员说：“**行，你慢慢试，我先去送后面几家的，你试好了在 App 上点一下‘确认’，我回头再来处理你的签收。**” 结果，公司只需要 5 个快递员，就能服务整条街的住户。

### 5. 什么时候它“不”灵？（重要补充）

虚拟线程有明确的适用边界：

1.  **CPU 密集型任务：** 如果你的代码是在做复杂的数学计算（比如加解密、视频转码），它会一直占用 CPU，没有阻塞。这时候用虚拟线程没有意义，因为系统线程没机会“跳走”去帮别人。
2.  **Synchronized 临界区中的阻塞（Pinning）：** Java 21 中，在 `synchronized` 监视器临界区内发生某些阻塞时，虚拟线程可能固定在载体线程上。应先缩短临界区并观察监控；只有确有长时间阻塞且适合替换时，再评估 `ReentrantLock`，不应机械替换所有 `synchronized`。

**总结：**
平台线程提供执行载体，虚拟线程提供轻量级任务视角；在支持的等待点，虚拟线程可以暂时脱离载体。最终效果取决于任务、JDK、操作系统和外部资源，不能用“永远不等待”或固定性能数字概括。
